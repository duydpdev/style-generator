# Build components from the theme

A component goes from theme to tokens to recipe to `cn` to markup. The code below mirrors `examples/design-system`, the workspace package the harness app builds its sample components on ([`examples/design-system/README.md`](../../examples/design-system/README.md)); every step imports only browser-safe subpaths (`./tokens`, `./cva`, `./recipes`, `./types`, `./ui`), so no Zod or Node code reaches the client bundle.

```text
src/theme.json            → the theme (source of truth)
style-gen.config.json     → every generator option (plugin, CLI)
src/theme.tokens.ts       → generated by the plugin / `style-gen generate` (commit it)
src/tokens.ts             → re-exports `tokens`, exports the theme's type
src/recipes/*.ts          → headless recipes (cva + createVariantMapper)
src/cn.ts                 → clsx + tailwind-merge aware of the theme's classes
src/axes.ts               → themeAxisAttributes(state), typed by ThemeAxesState
```

## 1. Theme

One JSON file ([Theme config](../reference/theme.md)) holds the design tokens; one config file holds every generator option. The Vite and Next plugins and the CLI read that same file, so the `@source inline` lines and the typed tokens cannot drift apart:

<!-- embed: examples/design-system/style-gen.config.json -->

```json
{
  "$schema": "./style-gen.config.schema.json",
  "theme": "src/theme.json",
  "output": "src/styles/theme.css",
  "tokensOutput": "src/theme.tokens.ts",
  "breakpoints": ["md", "lg"],
  "coverage": { "colors": { "opacities": [10, 20, 50, 80] } }
}
```

The literal `breakpoints` array narrows `(typeof tokens)["breakpoints"][number]` to `"md" | "lg"` in the generated tokens file. All keys: [Options](../reference/options.md).

## 2. Tokens

The plugin and `style-gen generate` write the browser-safe token keys next to the CSS as `theme.tokens.ts`. Commit that file and import `tokens` from it; `style-gen generate --check` fails in CI when it is missing or stale. Leave the file to Prettier: it carries a `// prettier-ignore` line before each export and nothing else, so exclude it from any other tool that rewrites files (Biome, dprint, oxfmt, ESLint stylistic `--fix`, a lint-staged glob), or `--check` reports it as stale ([Troubleshooting](../troubleshooting.md#tokens-file-missing-or-stale)). Import the theme JSON as a module (`resolveJsonModule`) to keep each key's literal type, and export both from one place:

<!-- embed: examples/design-system/src/tokens.ts -->

```ts
import type { ColorVariant } from "@duydpdev/style-generator/types";

import themeJson from "./theme.json";
import { tokens } from "./theme.tokens";

/** The theme's literal type — feeds `ColorVariant<Theme>`, `ThemeAxesState<Theme>`, … */
export type Theme = typeof themeJson;

export const theme = themeJson;

/** Browser-safe typed token arrays, generated from `theme.json` + `style-gen.config.json` into `./theme.tokens.ts` (commit it). */
export { tokens };

/** A color token key, or `key/step` with a step from `coverage.colors.opacities`. */
export type ColorValue =
  | ColorVariant<Theme>
  | `${ColorVariant<Theme>}/${(typeof tokens)["opacities"][number]}`;
```

`createDesignTokens(theme, options)` from `./tokens` is only for a second theme created at runtime. The arrays in `tokens` are listed in [Design tokens](../reference/tokens.md).

## 3. Recipe: `createVariantMapper` and `COLOR_STATES`

`createVariantMapper(prefix, keys)` turns token keys into class names. For sibling keys `primaryHover` and `primaryActive` in the theme, `{ states: COLOR_STATES }` merges them into the base key's class:

```ts
import {
  COLOR_STATES,
  createVariantMapper,
} from "@duydpdev/style-generator/cva";

import { tokens } from "./tokens";

const bg = createVariantMapper("bg", tokens.colors, { states: COLOR_STATES });
// bg.primary      → "bg-primary hover:bg-primary-hover active:bg-primary-active"
// bg.primaryHover → "bg-primary-hover"
// bg.danger       → "bg-danger"
```

Pass `COLOR_STATES` rather than typing `["hover", "active"]`: it is the list the `@source inline` lines use as well. Pass camelCase keys like the ones in `tokens.colors` (`primaryHover`, not `primary-hover`). `prefix` is typed as the prefixes the registry covers, so `createVariantMapper("fill", …)` is a type error: no `@source inline` line keeps that class. [`createVariantMapper`](../reference/cva.md) documents `allowUnregisteredPrefix` for the rare case you declare the classes yourself.

A headless recipe composes the mappers with `recipeFromTables` (class-variance-authority underneath); framework components wrap it. List the intents the component offers with `satisfies` on the color keys: rename or delete a color in `theme.json` and the compiler flags exactly that line instead of emitting a class that no longer exists.

<!-- embed: examples/design-system/src/recipes/button.ts#intents -->

```ts
/**
 * The semantic intents the components expose. `satisfies` is the DX anchor:
 * rename or remove one of these colors in `theme.json` and the compiler fails
 * here, on the exact line, instead of silently shipping a class that no
 * longer exists (an `Extract<…>` would silently drop it).
 */
export const intents = [
  "primary",
  "secondary",
  "success",
  "danger",
] as const satisfies readonly ColorVariant<Theme>[];

export type Intent = (typeof intents)[number];
```

`recipeFromTables(tables)` returns a `RecipeFn<typeof tables>`, typed by the variant names of its tables: do not annotate the result with the bare `RecipeFn`, which opts out of that check ([UI kit](../reference/ui.md#recipefromtables-recipetables-varianttable-recipeprops-recipefn-recipevariantprops)). Classes with an opacity modifier (`bg-primary/10`) are not covered by default: write them out literally in a source file Tailwind scans, or list the steps in `coverage.colors.opacities` ([`coverage`](../reference/options.md#coverage-trim-the-source-inline-lines-per-category)).

## 4. `cn`: merge classes with the theme's classes in mind

`tailwind-merge` does not know a theme's `text-16-medium`, `shadow-md` or `rounded-pill` by default, so it can keep the wrong class. `createCn` wraps `clsx` and a `tailwind-merge` extended with the theme's tokens; `class-variance-authority`, `clsx` and `tailwind-merge` stay dependencies of the application:

<!-- embed: examples/design-system/src/cn.ts -->

```ts
import { createCn } from "@duydpdev/style-generator/ui";

import { tokens } from "./tokens";

/** The design-system theme's `cn` (`createCn` from `@duydpdev/style-generator/ui`). */
export const cn = createCn(tokens);
```

`cn("rounded-md", "rounded-pill")` keeps the later class, and so do the theme's typography and shadow classes. Components call `cn(buttonRecipe({ … }), className)`.

## 5. Theme axes on the DOM

`themeAxisAttributes(state)` returns the `data-<axis-kebab>` attributes of the active axes; `"base"` or an omitted axis emits nothing. Type `state` with `ThemeAxesState` from the generated `theme.tokens.ts`, which lists the axes and variants of `theme.json`. It uses the same attribute-name formula as the CSS selectors, so the DOM and the CSS do not drift apart:

<!-- embed: examples/design-system/src/axes.ts -->

```ts
import { themeAxisAttributes } from "@duydpdev/style-generator/recipes";

import type { ThemeAxesState } from "./theme.tokens";

/**
 * The DOM attributes that switch the theme's axes on, typed by `theme.json`:
 * `axisAttributes({ theme: "highContrast", palette: "forest" })` →
 * `{ "data-theme": "high-contrast", "data-palette": "forest" }`. `"base"` (or
 * an omitted axis) emits nothing. Spread on `<html>`, or pass to Nuxt's
 * `useHead({ htmlAttrs })`.
 */
export const axisAttributes = (
  state: ThemeAxesState,
): Readonly<Record<string, string>> => themeAxisAttributes(state);
```

Spread the result onto `<html>` (React: `<html {...axisAttributes(state)}>`; Nuxt: `useHead({ htmlAttrs: axisAttributes(state) })`). A complete toggle is in the [cookbook](../cookbook.md#dark-mode-toggle).

## 6. Spacing props: `splitSpacingProps`

A component that accepts spacing props (`p`, `px`, `gap`, …, a number or `{ base, md, lg }`) separates them from the rest with `splitSpacingProps` from `./recipes`. `SpacingProps<(typeof tokens)["breakpoints"][number]>` takes its breakpoint keys from the generated tokens, so `{ xl: 4 }` is a type error when `xl` is not in `breakpoints`:

```ts
import {
  splitSpacingProps,
  type SpacingProps,
} from "@duydpdev/style-generator/recipes";

import { tokens } from "./tokens";

type Props = SpacingProps<(typeof tokens)["breakpoints"][number]> & {
  id: string;
};
declare const props: Props;

const { spacing, rest } = splitSpacingProps(props, tokens.spacingProperties);
// with props = { p: 4, mx: { base: 2, md: 4 }, id: "x" }:
// spacing.className → "sp-p sp-mx"
// spacing.style     → { "--sg-sp-p": "1rem", "--sg-sp-mx": "0.5rem", "--sg-sp-mx-md": "1rem" }
// rest              → the remaining props (className, children, …)
```

The class and the style variables go on the same element. [Spacing](../reference/spacing.md) shows a `Box` component and the rules.

## 7. Layout props: `splitLayout`

A layout component (`Box`, `Flex`, `Stack`, `Grid`) takes spacing, recipe variants and inline sizes as props. `splitLayout` sorts them in one pass: the recipe turns variant props into classes, `spacingKeys` become `.sp-*` classes and variables, `sizeKeys` become inline style (a number is px), and everything else stays in `rest`:

```ts
import { createVariantMapper } from "@duydpdev/style-generator/cva";
import {
  createCn,
  mergeStyle,
  recipeFromTables,
  splitLayout,
} from "@duydpdev/style-generator/ui";

import { tokens } from "./tokens";

const cn = createCn(tokens);
const box = recipeFromTables({
  base: "flex",
  variants: { rounded: createVariantMapper("rounded", tokens.borderRadius) },
});

declare const props: {
  rounded: "pill";
  p: number;
  width: number;
  className: string;
  id: string;
};

const split = splitLayout(props, {
  recipe: box,
  spacingKeys: tokens.spacingProperties,
  variantKeys: ["rounded"],
  sizeKeys: ["width"],
});
export const element = {
  ...split.rest,
  className: cn(split.className, props.className),
  style: mergeStyle(split.style),
};
```

`extra` (optional) holds the component's own variants, which win over props. The harness `Box` in [`examples/harness/src/ui/Box.tsx`](../../examples/harness/src/ui/Box.tsx) is the full version; the options are in [UI kit](../reference/ui.md#splitspacing-splitlayout-splitlayoutoptions-split).
