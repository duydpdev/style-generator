# Upgrading from 7.x to 8.0

8.0.0 moves every generator option into `style-gen.config.json`, makes the plugins and `style-gen generate` write a typed `theme.tokens.ts`, renames `backDropBlurs` to `backdropBlurs`, and removes migration code for versions that never reached npm.
The generated CSS, the `--sg-*` variables and the `@source inline` output are unchanged: regenerating `theme.css` after the upgrade produces the same file.

For earlier upgrades see [`6.x-to-7.0.md`](./6.x-to-7.0.md), [`5.x-to-6.0.md`](./5.x-to-6.0.md), [`4.x-to-5.0.md`](./4.x-to-5.0.md) and [`3.x-to-4.0.md`](./3.x-to-4.0.md). The full rules live in [`README.md`](../../README.md).

## Before you upgrade

Run this from your repository root. Every hit is handled by one of the sections below; a hit in an unrelated variable can be ignored:

```bash
grep -rnE "backDropBlurs|themePath|outDir|resolveSpacingProps|COLOR_STATES|splitLayout\(|themeAxisAttributes<|ResponsiveValueStrict|DefaultBreakpointKeys|SpacingKey\b|RecipeFn|extraSources" --include='*.ts' --include='*.tsx' --include='*.mts' --include='*.cts' --include='*.jsx' --include='*.vue' --include='*.js' --include='*.mjs' --include='*.cjs' --include='*.json' --exclude-dir=node_modules .
```

Pin the version exactly, change the config, the plugin call and the imports in one commit, run `style-gen schema` to regenerate the committed `theme.schema.json` and `style-gen.config.schema.json` (neither `generate` nor `init` rewrites them, so they keep the keys of 7.x), and run `style-gen doctor` and `style-gen generate --check` before merging. `style-gen schema` writes `theme.schema.json` next to the theme (`--out` must stay inside the project root) and `style-gen.config.schema.json` at the root (`--config-out`); an existing config does not get the `$schema` key, so add `"$schema": "./style-gen.config.schema.json"` as its first key by hand (only `init` for a new config writes it).

## B1. Plugins take only `root`

`styleGenVite` and `styleGenNext` no longer accept `themePath`, `outDir` or `options`. Every generator option lives in `style-gen.config.json` (or `package.json["style-gen"]`).
Move `themePath` to `theme`, `outDir` to the directory of `output`, and `options` to the same keys in the config file. `root` is the directory that holds `style-gen.config.json`; every path in the config resolves from it.
Passing any other key throws an error that points at this section.

Before:

```ts
// vite.config.ts
import { options } from "./src/options";

export default defineConfig({
  plugins: [
    styleGenVite({
      themePath: "src/theme/theme.json",
      outDir: "src/theme",
      options,
    }),
  ],
});
```

After:

```json
{
  "theme": "src/theme/theme.json",
  "output": "src/theme/theme.css",
  "coverage": { "colors": { "opacities": [10, 20, 50, 80] } }
}
```

```ts
// vite.config.ts
export default defineConfig({
  plugins: [styleGenVite()],
});
```

Next.js: `styleGenNext({ themePath, outDir, options })(nextConfig)` becomes `styleGenNext()(nextConfig)`.
Nuxt runs the config from another directory, so give it the root: `styleGenVite({ root: fileURLToPath(new URL(".", import.meta.url)) })`.

## B2. `theme.tokens.ts` is generated on every emit

The plugins and `style-gen generate` write `theme.tokens.ts` next to `theme.css` (config key `tokensOutput`; default: the directory of `output`).
App code imports `tokens` from it instead of calling `createDesignTokens(theme, options)`, so `options.ts` is deleted. `createDesignTokens` stays for a second theme created at runtime.
Commit the tokens file, keep `theme.css` git-ignored, and add `style-gen generate --check` to CI: it writes nothing and exits 1 when the tokens file is missing or differs from the theme and config.
The file exports `tokens`, `Tokens`, `themeAxes` and `ThemeAxesState`.
Prettier is the only formatter that leaves the file alone: it carries a `// prettier-ignore` line before each export and nothing else. Exclude `theme.tokens.ts` from every other tool that rewrites files (Biome, dprint, oxfmt, ESLint with a stylistic rule and `--fix`, a lint-staged glob): a rewrite makes `style-gen generate --check` report the file as out of date.

Before:

```ts
// src/theme.ts
import { createDesignTokens } from "@duydpdev/style-generator/tokens";

import { options } from "./options";
import themeJson from "./theme/theme.json";

export const tokens = createDesignTokens(themeJson, options).DesignTokens.Web;
```

After:

```ts
// src/theme.ts
import themeJson from "./theme/theme.json";

export { tokens, type Tokens } from "./theme/theme.tokens";
export const theme = themeJson;
```

```bash
style-gen generate --check
```

## B3. `style-gen tokens` default path

`style-gen tokens` now writes beside `output` (it wrote beside the theme file). `--out` is unchanged.

Before:

```bash
style-gen tokens
# wrote src/theme/theme.tokens.ts, next to theme.json
```

After:

```bash
style-gen tokens
# writes next to the file named by "output" in style-gen.config.json
```

## B4. `themeAxisAttributes` is not generic

`themeAxisAttributes<typeof theme>(state)` becomes `themeAxisAttributes(state)`. Type the state with `ThemeAxesState` from the generated file.
A state typed as an `interface` no longer compiles (TS2345: an interface has no implicit index signature, which `Record<string, string | undefined>` needs). Declare it as a `type` alias, or use `ThemeAxesState`.

Before:

```ts
import { themeAxisAttributes } from "@duydpdev/style-generator/recipes";

import type { theme } from "./theme";

const attributes = themeAxisAttributes<typeof theme>({ theme: "dark" });
```

After:

```ts
import { themeAxisAttributes } from "@duydpdev/style-generator/recipes";

import type { ThemeAxesState } from "./theme/theme.tokens";

const state: ThemeAxesState = { theme: "dark" };
const attributes = themeAxisAttributes(state);
```

## B5. `backDropBlurs` is now `backdropBlurs`

The theme key, `themeAxes.<axis>.<variant>.backdropBlurs`, `DesignTokens.Web.backdropBlurs`, `coverage.backdropBlurs`, `RecipeTokens.backdropBlurs` and the `createCn` input are renamed. The classes and the `--sg-backdrop-blur-*` variables do not change.
Find every hit with `grep -rl backDropBlurs .`.
A committed `theme.schema.json` still lists the old key, so regenerate it with `style-gen schema`; the schema of a 4.x project also gains the `typography.*.fontWeight` bounds (1 to 1000) and no longer lists `letterSpacing` as required. If you build your `tailwind-merge` instance with `createTailwindMergeExtension` (`./recipes`), its `TailwindMergeTokens` input reads `backdropBlurs` too: pass the tokens from `theme.tokens.ts` and the rename follows.

Before:

```json
{ "colors": { "primary": "#0af" }, "backDropBlurs": { "md": "12px" } }
```

After:

```json
{ "colors": { "primary": "#0af" }, "backdropBlurs": { "md": "12px" } }
```

## B6. One export site per symbol

The symbols named here are exported from one subpath only. `COLOR_STATES` comes from `@duydpdev/style-generator/cva` (removed from `./tokens`). `DefaultBreakpointKeys`, `ResponsiveValueStrict` and `SpacingKey` come from `@duydpdev/style-generator/types` (removed from `.` and `./spacing`). The theme, option and token types (`ThemeConfig`, `StyleGeneratorOptions`, `DesignTokensWeb`, `ColorVariant`, …) are still exported from both `.` and `./types`.

Before:

```ts
import { COLOR_STATES } from "@duydpdev/style-generator/tokens";
import type { ResponsiveValueStrict } from "@duydpdev/style-generator/spacing";
```

After:

```ts
import { COLOR_STATES } from "@duydpdev/style-generator/cva";
import type { ResponsiveValueStrict } from "@duydpdev/style-generator/types";
```

## B7. `resolveSpacingProps` is removed

Use `splitSpacingProps` (`./recipes`) or `splitSpacing` (`./ui`) for component props, or call `resolveSpacing` once per property.
Spacing props are camelCase: `gap-x` is the prop `gapX`. A kebab-case key such as `"gap-x"` is not a spacing prop, so `splitSpacing` leaves it in `rest` instead of turning it into a class.

Before:

```ts
import { resolveSpacingProps } from "@duydpdev/style-generator/spacing";

const { classNames, style } = resolveSpacingProps({
  p: props.p,
  m: props.m,
});
```

After:

```ts
import { splitSpacing } from "@duydpdev/style-generator/ui";

const { className, style, rest } = splitSpacing(
  props,
  tokens.spacingProperties,
);
```

## B8. `splitLayout` takes an options object

The positional arguments after `props` become one object.

Before:

```ts
const split = splitLayout(
  props,
  box,
  spacingKeys,
  variantKeys,
  sizeKeys,
  extra,
);
```

After:

```ts
const split = splitLayout(props, {
  recipe: box,
  spacingKeys,
  variantKeys,
  sizeKeys,
  extra,
});
```

## B9. `RecipeFn` is typed by its tables

`recipeFromTables(tables)` returns a function whose parameter type is derived from the tables, so a misspelled variant name (`intnet: "primary"`) is a compile error, and so is a value the table does not declare. Each variant accepts only its own option keys; a key `"true"`/`"false"` means a boolean, and a numeric key (`10`) accepts the number and its string form. These now fail with TS2322:

- a widened prop: `size: string`;
- a conditional that can be `false`: `cond && "sm"`;
- a `number` prop passed to a variant whose keys are numeric literals (`10 | 20`);
- a literal the table does not declare: `size: "xl"`;
- `true` or a number on a variant whose keys are plain strings.

Narrow the value (`cond ? "sm" : undefined`, a union type for the prop) or declare the option in the table. A `: RecipeFn` annotation still compiles: it only opts that recipe out of the check (`RecipeFn` is the loose `(props?: RecipeProps) => string`), so unknown names and values are accepted again. Remove the annotation to get the check; the names it now reports were silently ignored before.

To find the annotations and their imports, run `grep -rnE ':\s*RecipeFn\b|\bRecipeFn\b.*from' --include='*.ts' --include='*.tsx' --include='*.vue' --exclude-dir=node_modules .`: delete each `: RecipeFn` and the `type RecipeFn` import it leaves unused.

Before:

```ts
export const buttonRecipe: RecipeFn = recipeFromTables(buttonTables);
```

After:

```ts
export const buttonRecipe = recipeFromTables(buttonTables);
```

## B10. Migration helpers are removed

`style-gen doctor` no longer scans your source files for pre-5.0 `--sg-<color>` variables. `style-gen init` no longer drops or reports the removed config keys (`plugin`, `extraSources`, `axes`) of an existing config: a config that still has one is invalid, and `init` leaves it byte for byte as it was, with a warning (it keeps the `theme` and `output` it declares); when you pick another theme with `--theme` or the wizard, `init` merges only that `theme` into it and warns `style-gen.config.json is invalid and init only merged the theme into it; generate rejects it:`. Every command that reads the config (`generate`, `doctor`, the plugins) rejects such a key with `<key> → Unrecognized key`, so delete it by hand; declare runtime classes with your own `@source inline(...)` next to the generated import. A `themes` key in a theme file no longer gets its own rename message: it produces the same `Unrecognized key` error as any other unknown key.
If you are on 6.x or earlier, upgrade to 7.x first and follow those guides.

Before:

```json
{
  "theme": "src/theme/theme.json",
  "extraSources": ["hover:bg-{primary,secondary}"]
}
```

After:

```json
{ "theme": "src/theme/theme.json" }
```

## New in 8.0 (nothing to change)

`style-gen generate --check`; the `tokensOutput` config key; `style-gen schema` also writes `style-gen.config.schema.json` (`--config-out`), which editors use for the `$schema` key of the config file; `style-gen init --yes` answers every prompt with its default and never overwrites an existing file.

`init --yes` keeps an existing config: the theme and output it names stay as configured, and only the missing files are written. It exits 1 when that config is not valid or when `--theme` names another theme. A 7.x config that still has a removed key (`extraSources`, `axes`, `plugin`) is such a config, so delete the key by hand (B10) before you run it, or refresh only the agent rules with `style-gen init --rules-only` (the CSS lines it prints come from the config in the current directory: without one there, they are the defaults for a first config, so ignore them when your config lives in a subfolder). Without `--yes` and without a terminal, an `init` on a config that declares an existing theme exits 1 (`Files already exist`), valid or not. 8.0.2 also tightened the different-files rule of `generate`, `doctor`, `schema` and the plugins: a setup whose `output` reaches the theme, the tokens file, `style-gen.config.json` or `package.json` through another case or a symlink used to exit 0 and now exits 1, and the plugins throw at startup ([must be different files](../troubleshooting.md#must-be-different-files)).

```bash
style-gen schema --config-out style-gen.config.schema.json
style-gen init --yes
```

## Rollback

Pin 7.x (`yarn add @duydpdev/style-generator@7.2.1`), then revert the config, the plugin call and the imports.

```bash
yarn add @duydpdev/style-generator@7.2.1
```
