# Migrating from 3.x to 4.0.0

4.0.0 is a breaking release. The library now targets **Tailwind CSS v4 only**, exposes a single `generate()` entry point instead of a Tailwind plugin plus a safelist, validates every theme with a strict Zod schema, and replaces the single-axis `themes` field with multi-axis `themeAxes`.

This guide lists every breaking change, grouped by area, with a before/after for each. The order follows how you will usually hit them while upgrading. For the earlier subpath-exports change (3.x), see [`3.x-subpath-exports.md`](./3.x-subpath-exports.md).

## Upgrade checklist

1. Upgrade `tailwindcss` to `>=4.1.0`. Tailwind v3 is no longer supported (stay on the 3.x line if you cannot move).
2. Replace `createStyleSystem` / `createStylePlugin` with `generate()` and write the returned `css` to a file.
3. Replace `@plugin` and `@source "…/safelist.txt"` in your CSS with a single `@import` of the generated CSS.
4. Rename theme keys: `themes` → `themeAxes` (nested one level deeper), `border` → `borderWidth`.
5. Fix keys the strict schema now rejects (`_` in keys, unknown top-level keys, values containing unsafe characters).
6. Replace removed options (`safelistColors`, `layout`, `opacity`, …) — see [Removed options](#removed-options-and-the-safelist).
7. Update `createVariantMapper` calls (no third boolean; optional `{ states }`).
8. Update spacing consumers: `--sp-*` → `--sg-sp-*`, `classNames` is a string, `ResponsiveValue` → `ResponsiveValueStrict`.
9. Replace the CLI `safelist` command with `generate`; run `style-gen doctor` and `style-gen schema`.
10. Move any `[data-theme]` attribute to the `<html>` element.

## Requirements

| Item              | 3.x                           | 4.0.0                                                                            |
| ----------------- | ----------------------------- | -------------------------------------------------------------------------------- |
| `tailwindcss`     | `>=3.4.0 \|\| >=4.0.0` (peer) | `>=4.1.0` (peer). `@source inline(...)`, which the output relies on, needs 4.1+. |
| Tailwind v3       | Supported (auto-detected)     | Removed. No version detection, no `tailwindVersion` option.                      |
| Runtime `zod`     | Not a dependency              | `zod ^4` is a regular dependency (used by `ThemeSchema`).                        |
| `vite` (optional) | `^5 \|\| ^6 \|\| ^7`          | Unchanged.                                                                       |
| `typescript`      | `^5.0.0` (peer)               | Unchanged.                                                                       |

Later 4.x releases widened the optional peers to `vite ^5 || ^6 || ^7 || ^8` and `typescript ^5 || ^6`; the README peer table is current.

The browser-safe subpaths (`./tokens`, `./cva`, `./spacing`, `./types`) stay free of Zod; only the root barrel, `./vite`, `./next` and the CLI pull it in.

## Removed APIs and the new entry point

| 3.x                                                                                  | 4.0.0                                                                                                                                                                          |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `createStyleSystem(theme, options)` → `{ plugin, safelist, themeCss, DesignTokens }` | `generate(theme, options)` → `{ css, tokens, schema }`                                                                                                                         |
| `createStylePlugin`                                                                  | Removed. The generated CSS contains the `@utility`/`@theme` blocks the plugin used to register.                                                                                |
| `generateSafelist`, `safelist.txt`                                                   | Removed. `css` contains `@source inline(...)` lines (see below).                                                                                                               |
| `detectTailwindVersion`, `options.tailwindVersion`                                   | Removed (Tailwind v4 only).                                                                                                                                                    |
| `@duydpdev/style-generator/plugin` subpath                                           | Removed. `./next` is new; `./vite` is unchanged in name (options changed).                                                                                                     |
| `themeCss` (v4 only, from `createStyleSystem`)                                       | Part of `css`. The standalone `generateThemeCss(theme)` still exists but only emits `:root`, `themeAxes` blocks and `@theme inline`; use `generate()` for the complete output. |
| `DEFAULT_LAYOUT_CLASSES`, `DEFAULT_OPACITY_VALUES`, `DEFAULT_ZINDEX_VALUES`          | Removed with their options.                                                                                                                                                    |
| `StyleModule`, `ModuleConfig`, `InferSafelistClasses` types                          | Removed.                                                                                                                                                                       |
| `TailwindPlugin` type                                                                | Removed with `createStylePlugin`.                                                                                                                                              |
| `BorderVariant<T>` type                                                              | `BorderWidthVariant<T>` (plus new `FontFamilyVariant<T>`).                                                                                                                     |
| `defineTheme` / `defineOptions` from `./tokens`                                      | Root barrel (`.`) only, so Zod never reaches browser-safe subpaths.                                                                                                            |
| `ResponsiveValue`                                                                    | `ResponsiveValueStrict` (see [Strict types](#strict-types)).                                                                                                                   |

`generate()` always re-validates the theme against `ThemeSchema`, so `defineTheme()` is optional at runtime. It still gives you the type check and an early `ZodError` at the call site.

### Wiring: `@plugin` → `@import`

`generate()` returns a CSS string. Write it to a file and import it next to Tailwind — there is no plugin to register and no safelist to point `@source` at.

Before (3.x):

```ts
// plugins/theme-plugin.ts
import { createStyleSystem, defineTheme } from "@duydpdev/style-generator";
import themeJson from "../styles/theme.json";

const { plugin, safelist, themeCss } = createStyleSystem(
  defineTheme(themeJson),
);
export default plugin;
export { safelist, themeCss };
```

```css
@import "tailwindcss";
@import "./theme.css";
@plugin "./plugins/theme-plugin.ts";
@source "../styles/safelist.txt";
```

After (4.0.0):

```ts
import { writeFileSync } from "node:fs";
import { generate, defineTheme } from "@duydpdev/style-generator";
import themeJson from "../styles/theme.json";

const { css, tokens } = generate(defineTheme(themeJson));
writeFileSync("styles/theme.css", css, "utf8");
export { tokens }; // was `DesignTokens` from createStyleSystem
```

```css
@import "tailwindcss";
@import "./theme.css";
```

You rarely need to write that script yourself: `style-gen generate`, `styleGenVite` and `styleGenNext` all do it (see [CLI](#cli) and [Framework plugins](#framework-plugins)).

`generate()` output, in order: an `@theme` block with `--breakpoint-*` (the library's pixel-based `defaultScreens` merged with `options.screens`), `:root` `--sg-*` variables, one `html[data-<axis>="<variant>"]` block per `themeAxes` variant, an `@theme inline` block mapping `--sg-*` → Tailwind namespaces, border-width / typography / spacing `@utility` blocks, and the `@source inline(...)` lines. In application code prefer standard Tailwind classes and `var(--color-*)`; the `--sg-*` layer exists to break the circular reference that would otherwise appear when a theme switches `--color-primary` to `var(--color-primary)`. The emitted `--sg-*` variables are nevertheless part of the public output throughout 4.x (aliases resolve to them, hand-written CSS may read or override them) and keep their names; the 5.0 major renames the color variables to `--sg-color-<key>` and will list that as a breaking change.

## Spacing

| Aspect                                                | 3.x                                       | 4.0.0                                                                                                               |
| ----------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Inline variable                                       | `--sp-p`, `--sp-p-md`                     | `--sg-sp-p`, `--sg-sp-p-md`                                                                                         |
| Plugin-internal variable                              | `--tw-sp-p` (in a global `*` rule)        | Gone. Each `@utility sp-<key>` owns its full breakpoint fallback chain.                                             |
| Inheritance                                           | Custom properties inherited into children | Registered with `@property … { syntax: "*"; inherits: false }` (no `initial-value`).                                |
| `spacing.useMatchUtilities` (`sp-p-4`, `sp-p-[24px]`) | Optional JIT utilities                    | Removed. Use `resolveSpacing` (inline style) or Tailwind's native `p-[24px]`.                                       |
| `resolveSpacingProps().classNames`                    | `string[]`                                | `string` (space-joined)                                                                                             |
| Prop names                                            | `string`                                  | `SpacingKey`, a literal union inferred from `DEFAULT_SPACING_PROPERTIES` (`p`, `px`, …, `gap-x`, `gap-y`, `top`, …) |

**Same-element rule.** Because the variables no longer inherit, a `.sp-*` class only sees the `--sg-sp-*` variables declared on **the same element**. A parent's `--sg-sp-p` no longer leaks into a child that has `class="sp-p"` but no variable of its own (that leak was a correctness bug in 3.x: a child could silently pick up its parent's responsive padding). `resolveSpacing` / `resolveSpacingProps` already return the class and the style together, so passing both to the same element keeps working; hand-written markup that set the variable on an ancestor must move it onto the element that uses the class.

Before:

```tsx
const spacing = resolveSpacingProps({ p: 4, mx: { base: 2, md: 4 } });
<div
  className={[...spacing.classNames, className].join(" ")}
  style={spacing.style} // { "--sp-p": "1rem", "--sp-mx": "0.5rem", "--sp-mx-md": "1rem" }
/>;
```

After:

```tsx
const spacing = resolveSpacingProps({ p: 4, mx: { base: 2, md: 4 } });
<div
  className={[spacing.classNames, className].filter(Boolean).join(" ")}
  style={spacing.style} // { "--sg-sp-p": "1rem", "--sg-sp-mx": "0.5rem", "--sg-sp-mx-md": "1rem" }
/>;
```

Search your code, CSS and design-tool notes for `--sp-` and `--tw-sp-`; anything reading those variables directly will silently stop working.

## Strict types

| 3.x                                                                        | 4.0.0                                                                                                |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `ResponsiveValue<T, B>` accepted any string key (`(string & {})` fallback) | `ResponsiveValueStrict<T, B>` is the only responsive type; a typo like `{ typo: 4 }` is a type error |
| `resolveSpacing(prop: string, …)`                                          | `resolveSpacing(prop: SpacingKey, value: ResponsiveValueStrict<number>, unit?)`                      |
| `resolveSpacingProps(props: Record<string, …>)` → `classNames: string[]`   | `resolveSpacingProps(props: Partial<Record<SpacingKey, …>>)` → `classNames: string`                  |

```ts
// before
import type { ResponsiveValue } from "@duydpdev/style-generator/spacing";
type AppBreakpoints = "base" | "mobile" | "tablet";
export type Responsive<T> = ResponsiveValue<T, AppBreakpoints>;

// after
import type { ResponsiveValueStrict } from "@duydpdev/style-generator/spacing";
type AppBreakpoints = "mobile" | "tablet"; // "base" is always allowed
export type Responsive<T> = ResponsiveValueStrict<T, AppBreakpoints>;
```

`SpacingKey` and `DefaultBreakpointKeys` are exported from `./spacing`; `ResponsiveValueStrict` is also exported from `./types` and the root barrel. Values may be `undefined` per key (`Partial<Record<…, T | undefined>>`).

## Strict theme schema

`ThemeSchema` (Zod) is now the single source of truth. Every level is a `strictObject`, so **unknown keys are rejected** instead of silently ignored. `generate()`, `defineTheme()`, the CLI (`generate`, `doctor`), `styleGenVite` and `styleGenNext` all validate independently and report `path → message` lines. (`style-gen schema` only writes the JSON Schema file and validates the _config_ file, not the theme.)

- Only `colors` is required. Optional: `typography`, `shadows`, `backDropBlurs`, `borderRadius`, `fontFamily`, `borderWidth`, `themeAxes`, and `$schema` (a string, for editor autocomplete).
- **Key grammar (all token names, axis names and variant names):** starts with a letter or digit, then letters, digits or `-`. Spaces, leading dashes, `;`, quotes etc. are rejected because keys are echoed into CSS custom-property names and selectors.
- **`_` is rejected in every key** (D-S3). `toKebabCase` keeps `_` (`primary_active` → class `bg-primary_active`) while the typed tokens camelCase it away (`primaryActive`), so a mapper would emit `bg-primary-active` — a class that does not exist. Rename to camelCase (`primaryActive`) or kebab-case (`primary-active`). Relaxing this later would be non-breaking; tightening it later would not. The CLI and both framework plugins print the hint on the offending path (for example `colors.primary_active → Key must start with a letter/digit … use camelCase, e.g. primaryActive, or kebab-case, e.g. primary-active`); the same message covers every other key-grammar violation (leading `-`, spaces, quotes, …). On a thrown `ZodError` the hint is the nested `issue.issues[0].message` of the `invalid_key` issue.
- **Value grammar:** values must not contain `;`, `{`, `}`, `<`, `@`, `\`, `/*` or a line break, quotes must be balanced (so `fontFamily` stacks such as `"Plus Jakarta Sans", system-ui, sans-serif` stay valid), and since 4.1.0 parentheses and brackets outside quoted strings must be balanced too (`rgb(0 0 0` is rejected).
- **Kebab collisions:** two keys in the same record that kebab-case to the same name (`blue500` and `blue-500`) are rejected.
- **Typography:** each key must kebab-case into a valid Tailwind `@utility` name (no leading digit or dash); typography values may not start with `$` (see aliases).
- `fontWeight` in a typography entry is a `number`; `fontFamily` and `fontStyle` are optional strings. `letterSpacing` was required in 4.0.0 and is optional since 4.1.0 (an absent `letterSpacing` emits no `letter-spacing` declaration).

Rejected inputs surface as a `ZodError`; the CLI and both framework plugins format it as one `path → message` line per issue. Custom messages quoted in this guide (rename hint, integer names, aliases, overrides) appear verbatim in that output, including the key-grammar hint.

Every naming rule, with a rejected and an accepted example, is tabulated in the theme reference's [Key rules](../reference/theme.md#key-rules).

### 4.0.2 — stricter validation

4.0.2 closes gaps between what the schema accepted and what the generator emitted. Input that parsed on 4.0.0/4.0.1 can now throw a `ZodError`; typed code may need a type argument.

- **Leading uppercase run rejected.** A token key that starts with two or more uppercase letters (`CTA`, `ABtn`, `HTMLParser`) is rejected with a rename hint (`cta`, `abtn`, `htmlparser`): the class `createVariantMapper` produced from the typed token (`c-ta`) differed from the class the registry emitted (`cta`). A single capital (`Blue`) and an uppercase run after the first character (`primaryCTA`) are still accepted.
- **`generate()` validates its options.** `breakpoints`, `screens` and `spacing.properties` keys must follow the theme key grammar, and their values the value grammar; this closes `@import`/`@plugin` injection through options.
- **`generateThemeCss()` validates its theme** exactly like `generate()` does, instead of trusting the caller.
- **`borderWidth` vs `colors`.** A `borderWidth` key that kebab-cases to a `colors` key is rejected, because both emit `border-<key>`.
- **Types.** `DefaultBreakpointKeys` is now `"md" | "lg"` (the breakpoints the default spacing CSS covers). `resolveSpacing` and `resolveSpacingProps` take a `BKeys` type argument for custom `options.breakpoints` (`resolveSpacingProps<"md" | "lg" | "xl">(…)`).

## Theme keys

### `border` → `borderWidth`

`border` and the old border module are merged into a single `borderWidth` category. Rename the theme key; the library emits `border`, `border-x`, `border-y`, `border-t`, `border-r`, `border-b` and `border-l` utilities backed by `--sg-border-width-*` variables. Omitting `borderWidth` entirely falls back to Tailwind's own scale (`border-0/1/2/4`) through `@source inline`, with no custom CSS. A `borderWidth` key may not share a name with a `colors` key. Independent of this library, Tailwind v4 also changed the default border colour to `currentColor` (v3: `gray-200`), so a bare `border` utility no longer paints a grey line: add an explicit `border-<color>` class where you relied on the old default ([Tailwind upgrade guide](https://tailwindcss.com/docs/upgrade-guide#default-border-color)).

| 3.x                               | 4.0.0                                |
| --------------------------------- | ------------------------------------ |
| `"border": { "thin": "1px" }`     | `"borderWidth": { "thin": "1px" }`   |
| `DesignTokens.Web.borderOption`   | `DesignTokens.Web.borderWidthOption` |
| `options.border` (`ModuleConfig`) | Declare `borderWidth` in the theme   |

### New `fontFamily` category

`fontFamily: { "sans": "\"Plus Jakarta Sans\", system-ui, sans-serif" }` maps into Tailwind's own `--font-*` namespace, so `font-sans` exists without a hand-written `@theme { --font-sans: … }` block. Keys may not kebab-case to a Tailwind font-weight utility (`thin`, `extralight`, `light`, `normal`, `medium`, `semibold`, `bold`, `extrabold`, `black`) because both utilities share the `font-` prefix. `DesignTokens.Web.variantFontFamily` lists the keys.

### Aliases (`"$key"`)

A value of the form `"$<key>"` refers to another key **of the same category** and is emitted as `var(--<cssVarPrefix>-<kebab-key>)`. The prefix belongs to the category (`sg` for `colors`, `sg-shadow` for `shadows`, `sg-backdrop-blur`, `sg-radius`, `sg-font`, `sg-border-width`), so it is not always `--sg-<key>`. No more duplicating a hex value between `primary` and `blue500`:

```json
{
  "colors": { "blue500": "#3B82F6", "primary": "$blue500" },
  "shadows": { "base": "0 1px 2px rgb(0 0 0 / 0.1)", "card": "$base" }
}
```

```css
:root {
  --sg-blue-500: #3b82f6;
  --sg-primary: var(--sg-blue-500);
  --sg-shadow-base: 0 1px 2px rgb(0 0 0 / 0.1);
  --sg-shadow-card: var(--sg-shadow-base);
}
```

Rules enforced at parse time:

- The target is the **raw key** (`$blue500`), not its kebab form (`$blue-500` is rejected even though both kebab-case to `blue-500`).
- The target must exist in the same category and the alias graph must be acyclic (`a: "$b", b: "$a"` is an error naming the cycle).
- A value that starts with `$` but does not match `^\$<key>$` is an error.
- **Aliases are not supported in `typography`**: a `$`-prefixed typography value is rejected.
- Aliases resolve against the merged graph of each `themeAxes` override too (base ∪ override).

### Override keys must exist in the base

A `themeAxes.<axis>.<variant>` override may only redefine keys that already exist in the matching base record. An override-only key (say `colors.background` inside `dark` with no base `colors.background`) is rejected, because it would never reach `@theme inline` / `@utility` output and would silently produce no utility. Declare the key in the base theme and override its value.

## Removed options and the safelist

`generateSafelist`, `safelist.txt` and the CLI `safelist` command are gone. `generate().css` ends with registry-generated `@source inline(...)` lines instead — one line per token category (colors, typography, shadows, backdrop blurs, border radius, font family, border width), one per state that has sibling tokens (see [`createVariantMapper`](#createvariantmapper)), one brace-expanded `sp-{p,px,…}` line for the spacing utilities, then any `extraSources`. Two consequences worth knowing:

- Every color always has `bg-*`, `text-*` and `border-*` utilities, whether or not your source references them. There is no `safelistColors` switch any more. Expect the CSS to be somewhat larger than a 3.x build that left color safelisting off.
- Class names that you build at runtime (template literals) still cannot be seen by Tailwind's static scan; declare them with the new `extraSources` option.

`extraSources: string[]` — each entry is emitted verbatim as `@source inline("<entry>")` (Tailwind's brace expansion works). `generate()` rejects entries that are empty, longer than 512 characters, or contain `"`, `'`, `\`, `;`, `@`, `<`, `>` or a line break — the characters that could close the string and inject an at-rule.

```ts
generate(theme, { extraSources: ["hover:bg-{primary,secondary}"] });
```

| Removed option / API (3.x)                           | Replacement in 4.0.0                                                                                                                     |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `safelistColors`                                     | Not needed: colors come from `@theme inline` plus the always-emitted `@source inline` line.                                              |
| `layout` (`DEFAULT_LAYOUT_CLASSES`)                  | Tailwind content scanning for classes written literally; classes built at runtime → `extraSources`.                                      |
| `border`                                             | Declare `borderWidth` in the theme; default widths are `DEFAULT_BORDER_VALUES` (`0, 1, 2, 4`).                                           |
| `rounded`                                            | Declare `borderRadius` in the theme; defaults are `DEFAULT_ROUNDED_VALUES`.                                                              |
| `opacity`, `zIndex`                                  | Native Tailwind v4 utilities (`opacity-50`, `z-10`); runtime-built classes → `extraSources`. `DesignTokens.Web.zIndexOption` is removed. |
| `dynamicClasses`                                     | `extraSources` (same meaning, emitted as `@source inline`).                                                                              |
| `responsiveModules`, `modules`                       | Not configurable. `borderRadius` always gets the `<breakpoint>:` variants for the active `breakpoints`; nothing else is responsive.      |
| `spacing.useMatchUtilities`                          | `resolveSpacing` (inline style) or Tailwind's native `p-[24px]`.                                                                         |
| `generateSafelist()`, `safelist.txt`, CLI `safelist` | `generate().css` (contains `@source inline`); CLI `style-gen generate [--watch]`.                                                        |
| `createVariantMapper(prefix, tokens, isKeepFormat)`  | `createVariantMapper(prefix, tokens)` — always kebab-cased with the same `toKebabCase` the registry uses.                                |

Options that remain: `breakpoints`, `screens`, `enableResponsive`, `typography.cssVarDriven`, `spacing.enabled`, `spacing.properties`, and the new `extraSources`. TypeScript reports removed options as unknown properties; since 4.1.0, `generate()` rejects unknown option keys with a `ZodError` (in 4.0.0 plain-JS callers got no runtime error), so grep your configs for the names above.

## `createVariantMapper`

```ts
import {
  createVariantMapper,
  COLOR_STATES,
} from "@duydpdev/style-generator/cva";
```

| 3.x                                                      | 4.0.0                                                                                                       |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `createVariantMapper(prefix, tokens, isKeepFormat?)`     | `createVariantMapper(prefix, tokens)` — the boolean third argument is removed; a stray `true` is a TS error |
| Kebab-casing optional                                    | Always kebab-cased, so every class is one the registry emits `@source inline` for                           |
| State classes written by hand (`hover:bg-primary-hover`) | `createVariantMapper(prefix, tokens, { states })`                                                           |

`{ states }` collapses flat sibling tokens into one class string per base token. Declare `primaryHover` / `primaryActive` next to `primary` in `colors`, then:

```ts
const tokens = ["primary", "primaryHover", "primaryActive", "danger"] as const;
const bg = createVariantMapper("bg", tokens, { states: COLOR_STATES });
// {
//   primary: "bg-primary hover:bg-primary-hover active:bg-primary-active",
//   primaryHover: "bg-primary-hover",
//   primaryActive: "bg-primary-active",
//   danger: "bg-danger",
// }
```

- `COLOR_STATES` is `["hover", "active"]`, exported from `.`, `./tokens` and `./cva` (browser-safe). It is the single list behind both the mapper and the registry's `@source inline` state lines, so always pass `COLOR_STATES` rather than hard-coding the array.
- Sibling detection uses the tokens you pass, matched as `token + PascalCase(state)`. Pass the camelCase keys that `tokens.Web.variantColor` provides (`primaryHover`, not `primary-hover`): the registry side camelCases keys before matching, so the two only agree when the mapper also receives camelCase. A token with no sibling keeps its single plain class. Sibling tokens themselves are plain single classes.
- **State names are emitted kebab-cased** (D-S4): a state `focusVisible` produces the variant `focus-visible:` — a valid Tailwind variant name — in both the mapper and the `@source inline` lines. The sibling lookup still uses the Pascal-cased state (`primary` + `primaryFocusVisible`).
- The prefix array overload (`createVariantMapper(["border-x", "border-y"], tokens)`) returns a nested map and also accepts `{ states }`.
- Because the `@source inline` state lines are generated per state, only state pairs that actually exist in your theme add CSS.

## CLI

| 3.x                            | 4.0.0                                                                                                                                                                                                                                                                  |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `style-gen safelist [--watch]` | `style-gen generate [--watch]` — writes the full CSS (default `styles/theme.css`) instead of `safelist.txt`                                                                                                                                                            |
| —                              | `style-gen schema [--out theme.schema.json]` — writes the JSON Schema for editor autocomplete/unknown-key warnings                                                                                                                                                     |
| `style-gen init --tw v3\|v4`   | `--tw` is removed (Tailwind v4 only). `init` still scaffolds a small generator script (`--plugin` names its path) — it now calls `generate()` and writes `theme.css` instead of building a Tailwind plugin. `init --dark` scaffolds a `themeAxes.theme.dark` template. |
| `style-gen doctor`             | Validates JSON, then `ThemeSchema` (unknown keys, unsafe values, aliases). Adds collision warnings.                                                                                                                                                                    |

- `generate` flags: `--theme <path>`, `--out <path>`, `-w`/`--watch`. Positionals (`style-gen generate <theme> <out>`) still work; flags win. Writes are atomic (temp file + rename).
- Config resolution order is unchanged, per key: CLI flags → config file → defaults. The config file is `style-gen.config.json` when it exists, otherwise `package.json["style-gen"]`; the two are alternatives and are never merged (a malformed `style-gen.config.json` is reported, not replaced by the `package.json` section). The config key `output` now defaults to `styles/theme.css`; `breakpoints`, `screens`, `enableResponsive`, `extraSources`, `spacing` and `typography` are forwarded to `generate()`. Since 4.1.0, unknown keys (including legacy ones such as `responsiveModules`) make `generate` and `doctor` fail with the key's path.
- Add `"$schema": "./theme.schema.json"` to your theme and run `style-gen schema --out theme.schema.json` to get autocomplete and a warning on unknown keys. `doctor` no longer has a special "legacy v1 nested colors" check: a nested color is now an ordinary schema error with its path.
- **`doctor` collision warnings** (warnings only — the exit code is unchanged): schema-valid keys that collide with a Tailwind static utility, such as `none` in `colors` / `shadows` / `backDropBlurs` / `borderRadius`, digit-only `borderWidth` keys, `colors` keys `transparent` / `current` / `inherit`, and typography keys whose kebab form equals a built-in utility: a `text-*` one (`text-sm`, `text-center`, …), a numeric one (`h1` → `h-1`, `p2` → `p-2`) or a static one (`italic`, `truncate`, …). `themeAxes` overrides are not inspected separately: an override key must already exist in the base, so a collision is reported once through the base record. See [built-in utility name clashes](#built-in-utility-name-clashes).

## Framework plugins

### `./vite` — `styleGenVite`

Same import path, same job (emit `theme.css` on dev start, on build and when the theme file changes), different options. `tailwindVersion` and `safelistColors` no longer exist, and the plugin no longer writes `safelist.txt`.

```ts
// before
styleGenVite({
  themePath: "src/theme/theme.json",
  outDir: "src/theme",
  options: {
    tailwindVersion: 4,
    breakpoints: [Breakpoint.MD, Breakpoint.LG],
    safelistColors: true,
  },
});

// after
styleGenVite({
  themePath: "src/theme/theme.json",
  outDir: "src/theme",
  options: { breakpoints: [Breakpoint.MD, Breakpoint.LG] },
});
```

Remove `theme.css` and `safelist.txt` from your `@source` / import lines accordingly, and add `theme.css` to `.gitignore` if the theme JSON is your source of truth. The file is written synchronously in `configResolved`, before Tailwind scans; the examples list `styleGenVite` ahead of `tailwindcss()`.

### `./next` — `styleGenNext` (new)

For Next.js (webpack and Turbopack) — it does not import `next`, so there is no extra peer dependency.

```ts
// next.config.ts
import type { NextConfig } from "next";
import { styleGenNext } from "@duydpdev/style-generator/next";

const nextConfig: NextConfig = {};
export default styleGenNext({
  themePath: "app/theme/theme.json",
  outDir: "app/theme",
})(nextConfig);
```

It emits `theme.css` when Next evaluates the config in `phase-development-server` (`next dev`, which also watches the theme file) or `phase-production-build` (`next build`, and other commands that load the config in that phase); since 4.1.1 every other phase (`next start`, export, info, test) returns the config without reading the theme. `styleGenNext(opts)(nextConfig)` returns Next's `(phase, ctx) => config` function, so export its result directly. Import the generated file from your global CSS (`@import "./theme/theme.css";`).

Limitations:

- **Function-form Next config needs 4.1.1.** Since 4.1.1 a `(phase, { defaultConfig }) => config` function is called with Next's arguments and its result is used. On 4.0.x and 4.1.0 Next receives that function as the config instead of calling it: call your own function first and pass the resulting object.
- **Symlinks are not resolved.** `themePath` / `outDir` are checked against `process.cwd()` by logical path only (a literal `..` escape is rejected); a symlink inside the project whose target lies outside it is accepted. The Vite plugin uses the same guard against the Vite root.

## `themes` → `themeAxes`

The single-axis `themes` field is replaced by `themeAxes: Record<axisName, Record<variantName, ThemeOverride>>`, which supports several independent axes (light/dark, a brand palette, …) at once. A theme that still contains `themes` is rejected. The CLI, `styleGenVite` and `styleGenNext` print one `path → message` line per issue (`defineTheme()` and `generate()` throw the `ZodError` itself, whose issue carries `path: ["themes"]` and the message after the arrow):

```text
themes → "themes" was renamed to "themeAxes"; move themes.<name> to themeAxes.theme.<name>
```

While `themes` is present this rename error suppresses every other schema issue, so expect a second wave of errors (missing `colors`, `_` in keys, …) after you rename it.

The schema only sees the theme it is handed. Also grep tooling that is not part of the library (build scripts, codegen, CI helpers, design-token exporters) for the `themes` key: nothing there is validated, and a script still reading `theme.themes` will quietly get `undefined` after the rename.

Before / after:

```json
// 3.x
{
  "colors": { "primary": "#3B82F6", "background": "#FFFFFF" },
  "themes": { "dark": { "colors": { "primary": "#60A5FA", "background": "#111827" } } }
}

// 4.0.0
{
  "colors": { "primary": "#3B82F6", "background": "#FFFFFF" },
  "themeAxes": {
    "theme": { "dark": { "colors": { "primary": "#60A5FA", "background": "#111827" } } },
    "palette": { "forest": { "colors": { "primary": "#16A34A" } }, "sunset": { "colors": { "primary": "#EA580C" } } }
  }
}
```

Generated selectors, in declaration order, after `:root`:

```css
html[data-theme="dark"] { … }
html[data-palette="forest"] { … }
html[data-palette="sunset"] { … }
```

```html
<html data-theme="dark" data-palette="forest"></html>
```

Rules to know:

| Rule                             | Behavior                                                                                                                                                                                                                                                                                                                        |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Selector is pinned to `html`     | `data-*` attributes on a wrapper `<div>` no longer have any effect (3.x emitted a bare `[data-theme="dark"]`, which worked on any element). Move the attribute to `<html>`.                                                                                                                                                     |
| Why `html`                       | A `var()` alias resolves to the value computed at the element that **declares** the custom property. `--sg-primary: var(--sg-blue-500)` is declared on `:root`, so an override of `--sg-blue-500` on a wrapper never reaches it. Overrides only take effect when they sit on the same element as the declarations, i.e. `html`. |
| Attribute values are kebab-case  | The attribute name and value are the kebab form of the axis and variant keys: axis `colorScheme`, variant `highContrast` → `html[data-color-scheme="high-contrast"]`.                                                                                                                                                           |
| Precedence = declaration order   | Selectors have equal specificity `(0,1,1)`; the blocks are emitted in the order written in the theme (axes first, then variants). When two axes override the same token, **the axis declared later wins**.                                                                                                                      |
| Integer names are rejected       | Axis and variant names that are canonical integers (`0`, `100`, `2024`) are rejected: JS enumerates integer-like keys first (ascending) regardless of file order, silently inverting precedence. Use `contrast100` or `c100`. `007` and `2xl` are fine.                                                                         |
| Override keys must exist in base | See [Override keys must exist in the base](#override-keys-must-exist-in-the-base).                                                                                                                                                                                                                                              |

The integer-name error reads: `themeAxes axis name "100" is a canonical integer; JS object key order puts integer-like keys first (ascending) regardless of declaration order, which would silently break the "last declared wins" precedence — rename it (e.g. "contrast100" or "c100")` (with `variant` in place of `axis` for a variant name).

### What `themeAxes` does not cover

`themeAxes` overrides the `--sg-*` variables of the built-in categories per axis/variant. The following stay hand-written CSS; the shared design system (`examples/design-system`, consumed by the React, Next and Nuxt apps) shows all of them:

| Axis (source)                                                       | Content                                                                              | 4.0.0 handling                                                                                                                                                                                                                                            |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `theme` (`theme.json` → `themeAxes.theme.dark`)                     | override `--sg-*` colors + shadows                                                   | Generated by the library — `html[data-theme="dark"]`                                                                                                                                                                                                      |
| `palette` (`theme.json` → `themeAxes.palette.{forest,sunset,mono}`) | override `--sg-*` colors                                                             | Generated by the library — `html[data-palette="forest\|sunset\|mono"]`                                                                                                                                                                                    |
| compound `[data-theme="dark"][data-palette="…"]` (`palettes.css`)   | cross-axis override (dark × a specific palette)                                      | Stays hand-written CSS (outside the 4.0.0 `themeAxes` scope): one `ThemeOverride` cannot target two axes' attributes at once. Its `(0,2,0)` specificity beats either single-axis `html[data-…]` rule `(0,1,1)`, independent of where the file is imported |
| `voice`, `geometry`, `surface` (`style-guide.css`)                  | `--f-sans`, `--radius-sm`, `--shadow-sm`, and a nested `.sg-glass-target` child rule | Stays hand-written CSS: variables outside `--sg-*` and nested-child selectors are not representable by a `ThemeOverride`                                                                                                                                  |

### Built-in utility name clashes

A theme key whose class equals a Tailwind **static** utility is not rejected by the schema: `none` in `colors` / `shadows` / `backDropBlurs` / `borderRadius` (`bg-none`, `shadow-none`, `backdrop-blur-none`, `rounded-none`), digit-only `borderWidth` keys (`border-2`), typography keys that kebab-case to a built-in utility (`text-sm`, `text-center`, a numeric one such as `h1` → `h-1`, a static one such as `italic` or `truncate`), and color keys named `transparent` / `current` / `inherit`. Which rule wins is decided by Tailwind's implementation of that utility (additive, theme-wins, built-in-wins or invalid CSS depending on the utility), not by the theme. Rename such keys (`clear`, `flat`, `zero`) instead of relying on the cascade, and run `style-gen doctor` to list the clashes it can detect. Typography is the widest case: each key emits an `@utility <kebab-key>` that can shadow any utility with that name (`h1` → `h-1`), not only `text-*`; `doctor` only checks the `text-*` subset (font-size scale, text-align, text-wrap, text-overflow), so review other typography names yourself.

## Rollback

Nothing in 4.0.0 changes an already published 3.x version, so a rollback never needs a registry operation on the consumer side.

### 1. Consumer repository

Revert the commit that bumped the dependency, then reinstall.

- If you re-pinned from a verified pre-release to the stable version, `git revert` that pin commit (returns you to the pre-release you validated).
- If the whole migration broke, `git revert -m 1 <merge-commit>` (or revert the migration commits) to return to the last 3.x version, including the `theme.json` renames (`themeAxes`, `borderWidth`, aliases) and the CSS wiring changes.
- Then reinstall with your package manager (`pnpm install`, `yarn install`, …) and rebuild.
- If you consumed a local tarball (a `file:` dependency), restore the previous dependency spec in `package.json` and the lockfile the same way; the tarball itself is not tracked.

### 2. Library, after a stable release

- **Never unpublish.** Consumers pin exact versions in lockfiles; deleting a version breaks reproducible installs.
- If `4.0.0` is broken, point the `latest` dist-tag back at the last good version: `yarn npm tag add @duydpdev/style-generator@<good-version> latest` **[UNVERIFIED: dist-tag support on GitHub Packages through Yarn Berry]**. If that command is not supported, communicate the good version to consumers instead and rely on exact pins.
- Fix forward: land the correction with a `[fix]` commit (patch bump) so semantic-release cuts `4.0.1`. Do not re-tag or republish `4.0.0`.

### 3. Library, during the pre-release (DEV) phase

Revert the offending pull request on `develop`. Pre-release versions that were already published stay in the registry; consumers pin the previous `-DEV.N`. The next merge to `develop` cuts a fresh `-DEV.N`.
