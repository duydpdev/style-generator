# Migrating from 5.3 to 5.4

5.4.0 is a minor release. A valid theme and valid options generate the same CSS as in 5.3, plus the classes of four more color prefixes. Two kinds of theme that used to pass are now rejected (see [What now throws](#what-now-throws)); both already produced a class that carried two meanings.

This guide covers the delta from 5.3.x. The full rules live in [`README.md`](../../README.md) and [`reference/options.md`](../reference/options.md).

## Four more color prefixes

The `colors` category now feeds seven utility prefixes instead of three: `bg`, `text`, `border` and the new `ring`, `outline`, `divide` and `placeholder`. The default `@source inline` line for colors becomes:

```css
/* 5.3 */
@source inline("{bg,text,border}-{primary,background,foreground}");
/* 5.4 */
@source inline("{bg,text,border,ring,outline,divide,placeholder}-{primary,background,foreground}");
```

The same applies to the state lines (`hover:{bg,text,border,ring,outline,divide,placeholder}-{primary-hover}`) and to the opacity line of `coverage.colors.opacities`.

The compiled CSS grows with every color. Measured with `style-gen budget` on the built landing site and on the `/examples/v4` app of this repository:

| Built CSS                  | 5.3 (gzip) | 5.4 (gzip) |  Delta |
| :------------------------- | ---------: | ---------: | -----: |
| landing site               |    14890 B |    15520 B | +630 B |
| `/examples/v4` example app |     9513 B |    10053 B | +540 B |

Your delta scales with the number of color keys. To keep the 5.3 output, trim the prefixes; the result is byte for byte the 5.3 colors lines (pinned by `generateSourceInline.test.ts`):

```jsonc
// style-gen.config.json
{ "coverage": { "colors": { "prefixes": ["bg", "text", "border"] } } }
```

`createVariantMapper` accepts the four new prefixes (`createVariantMapper("ring", tokens.colors)`), because they are now registry prefixes. A prefix the registry does not emit, such as `fill`, is still a type error.

## What now throws

Each rule is reported as one `path → message` line by `formatZodError`.

### 1. A `colors` key that is also a Tailwind divider width

`divide-x` and `divide-y` are Tailwind's divider-width utilities, so a color named `x` or `y` would emit one class with a width and a color. A `colors` key is rejected when it kebab-cases to `x`, `y`, `x-<integer>`/`y-<integer>` (`divide-x-2`) or `x-<k>`/`y-<k>` where `<k>` is a `borderWidth` key of the same theme (`divide-x-thin`).

```jsonc
{ "colors": { "x": "#ffffff" } }
// → colors.x → colors key "x" collides with Tailwind's divider utility "divide-x" (borderWidth divide-x/y scale) — rename it.
```

Fix: rename the key. `xl`, `yellow`, `x2l` and `xReverse` stay valid (`xReverse` gets a doctor warning, see below).

### 2. A `typography` key equal to a color class

A `typography` key must not equal another category's class. With seven color prefixes this now includes `ring-<key>`, `outline-<key>`, `divide-<key>` and `placeholder-<key>`: `typography.ringPrimary` next to `colors.primary` is rejected, because both would be the class `ring-primary`.

```jsonc
{ "colors": { "primary": "#ffffff" }, "typography": { "ringPrimary": { … } } }
// → typography.ringPrimary → … ring-primary …
```

Fix: rename the typography key.

## New doctor warnings

`style-gen doctor` warns (exit code stays 0) for a `colors` key whose `ring-`, `outline-` or `divide-` class is a Tailwind built-in, because Tailwind decides which rule wins:

- statics: `ring-inset`, `outline-hidden`, `outline-solid`, `outline-dashed`, `outline-dotted`, `outline-double`, `divide-solid`, `divide-dashed`, `divide-dotted`, `divide-double`, `divide-x-reverse`, `divide-y-reverse` (so `inset`, `hidden`, `solid`, `dashed`, `dotted`, `double`, `xReverse`, `yReverse`);
- integer widths and offsets: `ring-3`, `outline-3`, `ring-offset-2`, `outline-offset-2` (so `"3"`, `offset2`).

Rename the key (`clear`, `flat`, `zero`) or accept that Tailwind's own rule applies.

## Typed opacity steps

`coverage.colors.opacities` is now also a typed token. `DesignTokens.Web.opacities` lists the steps ascending (`[]` without the option), and `OpacitySteps<O>` is the element type: the literal steps for literal options, `number` for an annotated `StyleGeneratorOptions`, `never` without the option. `createVariantMapper` adds `token/step` keys from it:

```ts
const web = createDesignTokens(theme, {
  coverage: { colors: { opacities: [10, 50] } },
}).DesignTokens.Web;

const bg = createVariantMapper("bg", web.colors, {
  opacities: web.opacities,
});
bg["primary/10"]; // "bg-primary/10"
```

State classes stay on the base key: `primary/10` never carries `hover:`. `{ opacities }` does not combine with `allowUnregisteredPrefix`.

The `theme.tokens.ts` module that `style-gen tokens` writes now includes `"opacities"` too (`[]` without the option). Regenerate it after upgrading; a module generated by 5.3 lacks the member.

`opacities` is a required member of `DesignTokensWeb`. If you build an object typed `DesignTokensWeb` by hand, add `opacities: []`.

## UI kit

For the `./ui` subpath: `splitLayout` passes a finite number variant value through (for example `zIndex: 10`) instead of dropping it, `RecipeProps` accepts numbers, and `RecipeTokens` gains an optional `opacities` member. Existing code keeps compiling.
