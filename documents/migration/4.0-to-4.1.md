# Migrating from 4.0 to 4.1

4.1.0 is a minor release, but it validates more than 4.0.x did. Input that used to pass silently now throws a `ZodError` whose issue path names the offending key, from `generate()`, `defineTheme()`, `style-gen generate` and `style-gen doctor`. Valid themes and options generate the same CSS as before. Most rejected input was already producing wrong or ignored output; the exceptions are a `breakpoints` entry whose width lives only in your own CSS (rule 4) and a key in the reserved `--sg-sp-*` namespace that happens not to overwrite a spacing variable (rule 1).

This guide covers the delta from 4.0.x. For the 3.x → 4.0 changes see [`3.x-to-4.0.md`](./3.x-to-4.0.md); the full rules live in [`README.md`](../../README.md) (key grammar, options reference, configuration file).

## What now throws

Each rule below is reported as one `path → message` line by `formatZodError`.

### 1. Two keys that produce the same CSS variable

Two keys in different categories whose `--<cssVarPrefix>-<kebab>` variable is identical are rejected, because the later one silently overwrote the earlier. The issue path is the key in the later category (in the order `colors`, `shadows`, `backDropBlurs`, `borderRadius`, `fontFamily`, `borderWidth`) and the message names both. Any key that produces a `--sg-sp-*` variable is rejected too: that namespace belongs to the spacing utilities.

```jsonc
// colors.shadowPrimary and shadows.primary both give --sg-shadow-primary
{ "colors": { "shadowPrimary": "#111111" }, "shadows": { "primary": "0 1px 2px #000" } }
// → shadows.primary → shadows.primary and colors.shadowPrimary both produce the CSS variable --sg-shadow-primary; …

// a color key that kebab-cases to sp-p collides with the spacing namespace
{ "colors": { "spP": "#111111" } }
// → colors.spP → colors.spP produces --sg-sp-p, which is reserved for the spacing utilities (--sg-sp-*); …
```

Fix: rename one of the keys.

### 2. Unbalanced `(` or `[` in a value

Parentheses and brackets outside quoted strings must balance, in every theme value (colors, shadows, typography, `themeAxes` overrides) and in `spacing.properties` values. Brackets inside a quoted string are ignored, so `"Brand (Display", serif` stays valid. (`screens` values must be a plain length, see rule 5.)

```jsonc
{ "colors": { "primary": "rgb(0 0 0" } }
// → colors.primary → Value has unclosed `(`: parentheses and brackets must be balanced
```

### 3. Unknown or mistyped option and config keys

`generate()` validates its options with a strict schema. An unknown key is rejected, also inside `spacing` and `typography`, and `enableResponsive`, `spacing.enabled` and `typography.cssVarDriven` must be booleans. `style-gen.config.json` (or `package.json["style-gen"]`) is validated with the same schema plus `$schema`, `theme`, `output` and `plugin`, so a typo in the file fails `generate` and `doctor` instead of being ignored. This includes legacy 3.x keys such as `responsiveModules`.

```jsonc
// options (programmatic) or style-gen.config.json
{ "breakpoint": ["md"] }
// → breakpoint → Unrecognized key: "breakpoint"

{ "spacing": { "enable": true } }
// → spacing.enable → Unrecognized key: "enable"

{ "enableResponsive": "false" }
// → enableResponsive → Invalid input: expected boolean, received string
```

An invalid `extraSources` entry in the config file is now reported as `Invalid config (style-gen.config.json):` with the path `extraSources.<i>`; before 4.1.0 it was reported as `Invalid options:`.

### 4. A `breakpoints` entry without a screen

Every `breakpoints` entry must name a screen in `defaultScreens` or in your `screens`; the issue path is the index of the offending entry.

```jsonc
{ "breakpoints": ["xl2"] }
// → breakpoints.0 → Breakpoint "xl2" has no screen width; add it to options.screens or use one of: sm, md, lg, xl, 2xl
```

Fix: if the width was defined only in your own CSS (`@theme { --breakpoint-3xl: … }`), move it into `options.screens` (or `screens` in `style-gen.config.json`).

### 5. `screens` that are not one length, or that mix units

Each `screens` value must be a single length in `px`, `rem` or `em`. The map merged with the (px) `defaultScreens` must use one unit, because breakpoints with mixed units sort incorrectly. This second issue is reported at the path `screens`.

```jsonc
{ "screens": { "md": "calc(1px)" } }
// → screens.md → Screen width must be a single length in px, rem or em (e.g. 768px, 48rem)

{ "screens": { "md": "48rem" } }
// → screens → screens must all use one unit after merging with the defaults (px: sm, lg, xl, 2xl; rem: md); …
```

Fix: use px, or override every default screen in the same unit.

## How to check before upgrading

Install 4.1.0, then run the doctor from the project root. It prints every issue with its path and exits 1 when the config or the theme is invalid:

```bash
yarn style-gen doctor        # or: npm exec --no -- style-gen doctor
```

To check a theme with the exact options your build passes, call `generate()` from the new version. Replace the theme path and the options with your own:

```bash
node --input-type=module -e "import {readFileSync} from 'node:fs'; import {generate, Breakpoint, formatZodError} from '@duydpdev/style-generator'; const t=JSON.parse(readFileSync('./path/to/theme.json','utf8')); try { const {css}=generate(t,{breakpoints:[Breakpoint.MD,Breakpoint.LG]}); console.log('THEME_OK', css.length); } catch (e) { console.log(formatZodError(e)); process.exit(1); }"
```

A `THEME_OK` line means the theme and options pass 4.1.0.

## Relaxed

`typography.*.letterSpacing` is optional. A typography entry without it emits no `letter-spacing` declaration, so inherited tracking is not reset. Existing themes that set it are unchanged. The generated JSON Schema no longer lists `letterSpacing` as required, so regenerate a committed `theme.schema.json` with `yarn style-gen schema` to get the same editor feedback.

## New export

`formatZodError` is exported from the root entry (`@duydpdev/style-generator`). It turns the `ZodError` thrown by `generate()` or `defineTheme()` into one `path → message` line per issue:

```ts
import { ZodError } from "zod";
import { formatZodError, generate } from "@duydpdev/style-generator";

try {
  generate(theme, options);
} catch (e) {
  if (e instanceof ZodError) console.error(formatZodError(e));
  throw e;
}
```
