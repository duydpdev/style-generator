# Migrating from 4.x to 5.0

5.0.0 is a breaking release. Most of the change is renames, but one of them (the color CSS variables) fails **silently**: a stale `var(--sg-primary)` resolves to nothing, so a swatch turns transparent and nothing errors at build time. Do the grep in [Before you upgrade](#before-you-upgrade) first.

For earlier upgrades see [`4.0-to-4.1.md`](./4.0-to-4.1.md) and [`3.x-to-4.0.md`](./3.x-to-4.0.md). The full rules live in [`README.md`](../../README.md).

## Before you upgrade

**1. Find every hand-written use of a color variable.** 5.0 emits color variables as `--sg-color-<key>` instead of `--sg-<key>`. Other categories already had their own prefix (`--sg-shadow-*`, `--sg-radius-*`, `--sg-font-*`, `--sg-border-width-*`, `--sg-backdrop-blur-*`) and keep it, as do the spacing variables (`--sg-sp-*`). Run this from your repository root; it matches both `var(--sg-<key>)` references and bare `--sg-<key>:` declarations, such as the axis overrides in a hand-written `palettes.css`:

```bash
rg --pcre2 -n -g '*.{css,scss,sass,less,ts,tsx,mts,cts,js,jsx,mjs,cjs,vue,svelte,astro,html}' \
  '(?<![\w-])--sg-(?!color-|shadow-|radius-|font-|border-width-|backdrop-blur-|sp-|typography-)[a-z0-9$]' .
```

`rg` (ripgrep) skips `node_modules`, `dist` and other git-ignored paths on its own. The PCRE flag `grep -P` is not available in the BSD `grep` that ships with macOS; use `rg`, or GNU grep (`ggrep` from Homebrew). The recipe cannot see one case that `yarn style-gen doctor` (5.0) does: a color key whose 4.x variable started with another category's prefix, such as `colorPrimary` (4.x `--sg-color-primary`) or `shadowPrimary` (4.x `--sg-shadow-primary`). In 5.0 `--sg-color-primary` means the key `primary`, so an old reference to `colorPrimary` silently shows the wrong color. If your colors have such keys, run `doctor` too and check those references by hand.

Every hit that names one of your color keys must become `--sg-color-<key>` (`--sg-primary` → `--sg-color-primary`, `--sg-blue-500` → `--sg-color-blue-500`). Skip the generated `theme.css`: regenerating it fixes it.

**2. Let `style-gen doctor` find them for you.** From 5.0 on, `doctor` scans every `.css`, `.scss`, `.sass`, `.less`, `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.vue`, `.svelte`, `.astro` and `.html` file under the project root (skipping the directories `node_modules`, `.git`, `dist`, `build`, `out`, `coverage`, `.next`, `.nuxt`, `.output`, `.svelte-kit`, `.turbo`, `.vercel` and `storybook-static`, files over 1 MiB and the generated file) and prints one warning per line that still uses a color key from your theme:

```text
src/theme/palettes.css:12: --sg-primary was renamed to --sg-color-primary in 5.0
```

The warning does not change the exit code. A variable that is not a color key of your theme (your own `--sg-brand`, say) is not reported.

**3. Pin the version exactly.** A `^` range on a pre-release (`^5.0.0-DEV.1`) matches every later `5.0.0-DEV.N` and every stable `5.x`, so an install or a lockfile refresh can pull in a newer breaking `DEV` build. Pin the exact version (`5.0.0-DEV.N`, then `5.0.0` once it ships), change your CSS and the pin in one commit, and build before merging.

**4. Regenerate `theme.css`** once the pin is bumped (the generated file is rewritten in full).

**5. Check the `tailwindcss` peer.** The peer range narrowed from `>=4.1.0` to `^4.1.0`: the generated CSS is Tailwind v4 dialect (`@theme inline`, `@utility`, `@source inline`, the `--border-width-*` namespace) and nothing is tested beyond 4.x.

## Breaking changes

### Colors

| 4.x                                                         | 5.0                                                 |
| ----------------------------------------------------------- | --------------------------------------------------- |
| `:root { --sg-primary: #3b82f6 }`                           | `:root { --sg-color-primary: #3b82f6 }`             |
| `--color-primary: var(--sg-primary)`                        | `--color-primary: var(--sg-color-primary)`          |
| alias `"$blue500"` → `var(--sg-blue-500)`                   | alias `"$blue500"` → `var(--sg-color-blue-500)`     |
| axis override `html[data-theme="dark"] { --sg-primary: … }` | `html[data-theme="dark"] { --sg-color-primary: … }` |

Why: every category now owns a distinct `--sg-<category>-` namespace. In 4.x a color key `shadowPrimary` and a shadow key `primary` both produced `--sg-shadow-primary`, which 4.1 had to reject. After the rename that collision cannot happen, so the cross-category variable check (and its error, `… both produce the CSS variable …`) is gone: `colors.shadowPrimary` + `shadows.primary` and `colors.spP` are valid themes now.

The Tailwind classes (`bg-primary`, `text-primary`, …) and `var(--color-primary)` are unchanged, so code that only uses utilities needs no edit. Only hand-written CSS or TypeScript that reads or overrides the intermediate `--sg-*` variable does.

### borderWidth

`borderWidth` no longer emits `@utility border-*` blocks. It now feeds Tailwind's `--border-width-*` theme namespace in `@theme inline`, so Tailwind builds the utilities itself:

```css
/* 4.x */
@utility border-thin {
  border-width: var(--sg-border-width-thin);
}
@utility border-x-thin {
  border-left-width: …;
  border-right-width: …;
}
/* … border-y/t/r/b/l */

/* 5.0 */
@theme inline {
  --border-width-thin: var(--sg-border-width-thin);
}
```

What changes for you:

- More utilities resolve: `border-s-<key>`, `border-e-<key>`, `divide-x-<key>` and `divide-y-<key>` work next to `border`, `border-x/y/t/r/b/l`. The `@source inline` border line gains `border-s`, `border-e`, `divide-x`, `divide-y` (appended after `border-l`), so a dynamically built `divide-x-thin` is generated too. `ring-*` and `outline-*` use other namespaces and are not covered.
- The exported `borderProperties` (from `.` and `./tokens`) gains `border-s`, `border-e`, `divide-x` and `divide-y`, so `createVariantMapper(borderProperties, …)` returns four more nested keys.
- A theme **without** `borderWidth` also gains `border-s`/`border-e`/`divide-x`/`divide-y` classes for `0`, `1`, `2` and `4` (16 classes) in its `@source inline` line.
- A compiled `.border-<key>` is now Tailwind's own rule shape: it also sets `border-style: var(--tw-border-style)` (like `border-2`), where the old `@utility` set only the width. `--tw-border-style` defaults to `solid`, and Tailwind's preflight already gives every element `border-style: solid`, so rendered borders do not change, with one exception: a `border-style` set in a lower cascade layer (`@layer base`/`components`, or a library's layered CSS) on an element that also has `border-<key>` is now overridden to `solid`. Use `border-dashed` and the other style utilities (they set the variable) or unlayered CSS.
- `colors` and `borderWidth` keys must still not kebab-case to the same name (both emit `border-<key>`); that check is unchanged.
- **Caveat:** `--border-width-*` is a Tailwind v4 theme namespace that tailwindcss.com does not document (a Tailwind maintainer remarked in [discussion #16875](https://github.com/tailwindlabs/tailwindcss/discussions/16875) that it might be deprecated). It works on tailwindcss 4.1 through 4.3, and `src/__integration__/tailwind-compile.test.ts` compiles `border-thin`, `border-s-thin` and `divide-x-thin` through the real engine, so a Tailwind release that drops it fails CI here before it reaches you. If that happens the previous generator can be restored from `git show a3e652f:src/features/theme-css/generateBorderWidthCss.ts` behind the same descriptor, with no API change.

### Spacing

`spacing.properties` maps a spacing key to the CSS properties it sets. In 4.x the map values (`var(--sg-sp-<key>)`) were never read, only the keys of each inner object, so 5.0 takes the list of properties directly. The variable is always `var(--sg-sp-<key>)`.

```ts
// 4.x
spacing: {
  properties: {
    inset: { top: "var(--sg-sp-inset)", bottom: "var(--sg-sp-inset)" },
  },
}

// 5.0
spacing: {
  properties: { inset: ["top", "bottom"] },
}
```

`DEFAULT_SPACING_PROPERTIES` has the same shape (`p: ["padding"]`, `px: ["padding-left", "padding-right"]`, …), as does the `SpacingPropertyMap` type (`Record<string, readonly string[]>`). Generated CSS is byte-identical. `spacing.properties` entries are validated as CSS property names (lowercase, e.g. `padding`, `column-gap`, `--custom`), and an empty array is rejected. A config file (`style-gen.config.json`) uses the same array form.

### Breakpoints

`Breakpoint` is a `const` object plus a type of the same name instead of a TypeScript `enum`:

```ts
export const Breakpoint = {
  SM: "sm",
  MD: "md",
  LG: "lg",
  XL: "xl",
  XXL: "2xl",
} as const;
export type Breakpoint = (typeof Breakpoint)[keyof typeof Breakpoint];
```

`Breakpoint.MD` is still `"md"`, so `breakpoints: [Breakpoint.MD, Breakpoint.LG]` needs no change. What changes: `const b: Breakpoint = "md"` now compiles (an enum would not accept the string literal). `Breakpoint.MD` and `Object.values(Breakpoint)` behave as before, and `Breakpoint` as a type is the union `"sm" | "md" | "lg" | "xl" | "2xl"`. Enum-member types no longer compile: `let x: Breakpoint.MD` and `type T = Breakpoint.LG | Breakpoint.XL` fail with TS2702; use the literals (`"md"`) or `typeof Breakpoint.MD`.

### Token naming

The arrays of `DesignTokens.Web` are named after the `ThemeConfig` field they come from:

| 4.x                   | 5.0             |
| --------------------- | --------------- |
| `variantColor`        | `colors`        |
| `variantText`         | `typography`    |
| `variantShadow`       | `shadows`       |
| `variantBackdropBlur` | `backDropBlurs` |
| `variantFontFamily`   | `fontFamily`    |
| `borderWidthOption`   | `borderWidth`   |
| `roundedOption`       | `borderRadius`  |

`spacingProperties`, `breakpoints` and `screens` keep their names. The values are identical: only the property names change. `createVariantMapper("bg", DesignTokens.Web.variantColor)` becomes `createVariantMapper("bg", DesignTokens.Web.colors)`.

Five type helpers are removed: `InferColorKeys`, `InferTypographyKeys`, `InferShadowKeys`, `InferBackdropBlurKeys` and `InferFontFamilyKeys` (from `.` and `./types`). Replace them with `CategoryTokenKey<TTheme, "colors">` (`"typography"`, `"shadows"`, `"backDropBlurs"`, `"fontFamily"`) or the semantic aliases `ColorVariant<T>`, `TextVariant<T>`, `ShadowVariant<T>`, `BackdropBlurVariant<T>`, `FontFamilyVariant<T>`. Note the behaviour difference: the four non-color helpers returned the **raw** theme keys (`"body-lg"`), while the runtime arrays and `CategoryTokenKey` are camelCased (`"bodyLg"`), so those helpers never matched `DesignTokens.Web.*`. `InferRoundedOptions`, `InferBorderWidthOptions` and `InferSpacingKeys` stay.

### Typography

- `fontWeight` must be a number from 1 to 1000 (CSS Fonts 4 `font-weight`). Fractions are accepted, because variable fonts use them (`450.5`); `0`, `1001`, negative numbers and `NaN` are rejected at `typography.<key>.fontWeight`.
- A typography key that kebab-cases to `sp-*` or `font-*` is rejected at `typography.<key>`, because its `@utility` would shadow the spacing utilities (`sp-*`) or the font-family and font-weight utilities (`font-*`). Rename it (`spBody` → `body`, `fontBold` → `strong`). A key that merely starts with those letters (`spacious`, `fonts`) is fine.

### Build-tool integrations (`styleGenVite`, `styleGenNext`)

- **Vite emits in `buildStart`, not `configResolved`.** `theme.css` is now written in `buildStart`, which Vite runs on `listen()`, in `middlewareMode`, and for SSR environments, and at the start of every build, still before Tailwind scans. The plugin sets `perEnvironmentStartEndDuringDev: true`, so on Vite >= 6 `buildStart` also runs for `createServer()` without `listen()` followed by `ssrLoadModule`. `closeBundle` no longer re-emits. The theme is registered with `this.addWatchFile`, so `vite build --watch` rebuilds on theme edits, and in dev the plugin adds the theme to `server.watcher`, re-emits after a debounce and sends `full-reload` **only when the CSS changed**. A failure now fails `buildStart` with a staged message: `Invalid JSON in <file>`, `Invalid options:`, `Invalid theme (<path>):`, `Invalid theme/options:`, `Failed to generate CSS: …` or `Cannot write <file>`. Code that created the dev server with `createServer()` and expected `theme.css` to exist _before_ any of those must `await server.listen()` (or use `middlewareMode`, or an SSR transform on Vite >= 6) first. The plugin releases its duplicate-instance registration when the dev server closes.
- **No-argument form.** `styleGenVite()` and `styleGenNext()` (no options object) read `style-gen.config.json`, else `package.json["style-gen"]`, from the Vite root (Next: `process.cwd()`): `theme`, `output` (the CSS file to write) and every `generate()` option in it. A malformed or schema-invalid config throws `[style-gen-vite] Invalid config (<source>):` (`[style-gen-next]` for Next) followed by one `path → message` line per issue; there is no silent fallback to defaults. Passing options keeps the 4.x behaviour and does not read the file.
- **Plugins read the config once.** The no-argument forms (`styleGenVite()` in `vite.config.ts`, `styleGenNext()` in `next.config.ts`) resolve `style-gen.config.json` when the bundler loads its config (Vite: `configResolved`; Next: when `next.config.*` is evaluated). An edit to the config file while `vite`/`next dev` is running is not picked up until you restart the dev server, whereas `style-gen generate --watch` re-reads it on every change. Keep the config in one place: the options object of an argument form (`styleGenVite({ themePath, outDir, options })`, as the examples do with the `options` exported by `examples/design-system/src/style-gen.options.ts`) never reads the file.
- **Next.** The function-form config `(phase, { defaultConfig }) => config` is called with Next's real arguments (the wrapper returns Next's `(phase, ctx) => config`); only `phase-development-server` and `phase-production-build` touch the disk. The dev watcher no longer dies when an edit makes the theme invalid: the error is logged, the last good `theme.css` stays, and the watcher is replaced when the config is loaded again with another theme, output path or set of generator options.
- **Path rules (`resolveProjectPath`).** `themePath` may be absolute or outside the project root (a shared theme in a monorepo package); `outDir` and `output` must stay inside it (`<label> escapes project root: <input>`). Every path is normalised (`..`, `.` and doubled separators are resolved) before it is compared or used as a watcher/output key. `src/shared/resolveSafePath.ts` is removed (it was internal), and the CLI's silent rewrite of a leading `/` into a project-relative path is gone: `--theme /abs/theme.json` now means the absolute path. If you passed `/styles/theme.json` meaning `<cwd>/styles/theme.json`, drop the leading slash. The symlink limitation (no `realpath`) is unchanged. Two plugin instances writing the same output **file** (not merely the same `outDir`) trigger the duplicate-target warning.

### CLI

- **Exit codes and `--help`.** Every command returns an exit code and none calls `process.exit`: `0` on success, `--help`, `--version` or a cancelled prompt; `1` on failure (also an unknown command); `style-gen budget` uses `2` for usage errors. `style-gen <command> --help` prints that command's options.
- **Strict flags.** Flags are parsed per command and an unknown flag is an error (`style-gen generate --them x` used to be ignored and fall back to the default theme). Scripts that passed extra flags to a command must drop them.
- **Invocations that now fail (exit `1`).** Each is rejected before any file is read or written, with the command's usage text:

  | Invocation                                                                    | Why and what to use                                                                                                                       |
  | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
  | `style-gen schema --theme <path>`                                             | `schema` takes only `--out`; it reads the theme from the config (`style-gen.config.json`)                                                 |
  | `style-gen doctor --theme <path>`                                             | `doctor` takes no flags; it reads the config from the current directory                                                                   |
  | `style-gen -w generate`, `style-gen --out x generate`                         | Only `--help`/`-h` and `--version`/`-v` may precede the command (`Unknown option: -w`); put the flag after it: `style-gen generate -w`    |
  | `style-gen doctor <path>`, `style-gen schema <path>`, `style-gen init <path>` | These commands take no positional arguments; use `--out` (`schema`) or `--theme`/`--plugin` (`init`); `doctor` has nothing to point at it |

  `generate` still accepts the positional form `generate <theme> <out>` (flags win over it), and `tokens` takes flags only. `style-gen budget` exits `2` instead of `1` for the same kind of usage error.

- **`generate` writes only when the content changed**, so an unchanged re-run leaves the file's mtime alone.
- **`generate --watch` follows the config.** It watches `style-gen.config.json` (or the `package.json` section) next to the theme and re-reads it on every change. An invalid edit is reported and the last valid config stays in effect. A theme that cannot be read at startup (missing, a directory) exits `1` before any watcher starts.
- **`doctor`.** A config error now stops the run (later checks would use the wrong defaults); it validates the theme _together with_ the config's options (`❌ Invalid theme/options`: stale `$`-alias holders under `axes.scope: "element"`, clashing attributes, `resetTailwindDefaults` without its category); an `output` or `plugin` outside the project root is an error; and it prints an **alias hint** for a `themeAxes` override whose literal repeats the value of another base key (`use "$white"`). A base key that any variant of any axis redefines is never suggested (axes stack on `html`, so aliasing it would change the value under that variant). The hint is a warning and never changes the exit code.

### Variant named `base`

`ThemeSchema` now rejects `themeAxes.<axis>.base`. `"base"` is the "no override" value of `ThemeAxesState` and `themeAxisAttributes()`, so such a variant could never be switched on. Rename it (`default`, `standard`) and update the `data-<axis>` attribute your code sets. An _axis_ named `base` is still valid.

### Stricter theme validation

`ThemeSchema` also rejects four themes that 4.x accepted but that produced broken CSS. Each is a `ZodError` at the path shown; `yarn style-gen doctor` reports it with that path.

- **Alias cycles across axes** (`themeAxes.<axis>.<variant>.<category>.<key>`). Every axis's block applies to the same `html` element at once, so `x.one: { colors: { a: "$b" } }` next to `y.two: { colors: { b: "$a" } }` makes `--sg-color-a` and `--sg-color-b` invalid while both variants are active. The schema walks every combination of at most one variant per axis (later-declared axes win a key) and reports a cycle at the later axis, naming the co-active pair. Point one of the aliases at a literal, or move both edges into one axis (two variants of the same axis are never active together).
- **`fontFamily` keys that start with `weight` or `size`** (`fontFamily.<key>`): `weightBold` emits `--font-weight-bold`, which is Tailwind's font-weight scale, not a family, and it overwrites `font-bold`. Rename it (`weightBold` → `display`).
- **A `typography` key equal to another category's class** (`typography.<key>`): `typography.textPrimary` emits `@utility text-primary`, the class `colors.primary` already emits (`bg-`/`text-`/`border-<key>`, `shadow-<key>`, `rounded*-<key>`, `border*-<key>` and `backdrop-blur-<key>` likewise). Rename the typography key (`textPrimary` → `bodyPrimary`) or the other token.
- **Two variants of one axis that kebab-case to the same attribute value** (`themeAxes.<axis>.<variant>`): `darkMode` and `dark-mode` both become `html[data-theme="dark-mode"]`, so the second block silently merges into the first. Rename one.

### Package types (`.d.cts`)

`package.json#exports` now nests the conditions: `import` resolves to `{ types: .d.ts, default: .js }` and `require` to `{ types: .d.cts, default: .cjs }`, and the top-level `types` field is gone. A CommonJS consumer under `moduleResolution: node16`/`nodenext` gets declarations that match its module format instead of the "masquerading as ESM" mismatch; `yarn check:types-pack` verifies this with `@arethetypeswrong/cli` (node16 profile). `moduleResolution: node10` (the legacy `"node"`) is unsupported, as before: the package has no `typesVersions`, so no subpath resolved there.

`dist/*.d.cts` is its `dist/*.d.ts` with one rewrite (`scripts/cjs-declaration.mjs`): the `vite` import becomes `import type { Plugin as Plugin_2 } from 'vite' assert { 'resolution-mode': 'import' }`. A `.d.cts` resolves its imports with the `require` condition, and Vite has no usable CommonJS types (5/6: an `export = any` stub without `Plugin`, `TS2305`; 7/8: ESM-only, `TS1479`), so the copy must resolve it as ESM. `assert`, not `with`, because `with` is a parse error on TypeScript < 5.3 even under `skipLibCheck`. **Limitation:** on TypeScript 5.0–5.2 a CommonJS consumer with `skipLibCheck: false` sees one `TS4125` on that line; `skipLibCheck: true` (the default in most setups) and TypeScript >= 5.3 are clean. The repo's `yarn typecheck:dist` checks the `.d.ts` under `module: ESNext` + Bundler and the `.d.cts` as a CommonJS consumer under `module: node16` with `skipLibCheck: false`; `yarn check:types-pack` (attw, node16) covers the `exports` conditions.

### Types

Almost all of this is types only; the exceptions are the runtime field `aliasedColors` and the `toKebabCase` export, both listed below. Each type item can turn into a compile error in code that compiled on 4.x, and each one is meant to: it reports a mismatch that 4.x let through.

- **Token arrays are `readonly`.** Every array of `DesignTokens.Web` (`colors`, `typography`, …, `spacingProperties`, `breakpoints`) is `readonly K[]`, not `K[]`. Reading, `.map`, `.includes` and spreading are unaffected; `.push` and assigning to a `K[]` variable fail. Copy first: `const colors = [...DesignTokens.Web.colors]`. `createVariantMapper` already takes `readonly T[]`.
- **`breakpoints` and `spacingProperties` follow your options.** `generate()`, `createDesignTokens()` and `defineOptions()` take `const O extends StyleGeneratorOptions`, and the result is `DesignTokensResult<TTheme, O>` / `DesignTokensWeb<TTheme, O>`. `generate(theme, { breakpoints: ["md", "xl"] }).tokens.Web.breakpoints` is `readonly ("md" | "xl")[]` (4.x: `string[]`); omitted, it is `readonly ("md" | "lg")[]`; `spacing.properties: { inset: [...] }` gives `spacingProperties: readonly "inset"[]` (4.x: `SpacingKey[]`, a lie for custom keys). Options typed as `StyleGeneratorOptions` (a variable annotated that way, or the Vite/Next plugin options) widen both to `readonly string[]`. `BreakpointKeys<O>` and `SpacingKeys<O>` are exported from `.` and `./types`; pass `BreakpointKeys<typeof options>` as `BKeys` to `resolveSpacing` / `ResponsiveValueStrict`.
- **`screens` is `Readonly<Record<Breakpoint | ScreenKeys<O>, string>>`** (4.x: `Record<string, string>`): the five default screens, which are always present, plus the keys `options.screens` adds. Indexing a key you never declared is now an error.
- **`StyleGeneratorOptions` arrays are `readonly`:** `breakpoints?: readonly (Breakpoint | (string & {}))[]` and `extraSources?: readonly string[]`; `SpacingPropertyMap` is `Readonly<Record<string, readonly string[]>>`. A `const` options object (`as const`) is now assignable; a function that took `options.breakpoints` as a mutable `string[]` must accept `readonly string[]`.
- **Unknown option keys are a compile error.** `generate()`, `createDesignTokens()` and `defineOptions()` type `options` as `ExactOptions<O>` (exported from `.` and `./types`): a misspelled top-level key (`generate(theme, { screnes })`) fails to compile, as it did in 4.x, and so does a variable of a wider type, such as an `interface` that extends `StyleGeneratorOptions` or a loaded config object that still carries `$schema`/`theme`/`output`. Pass only the generator keys. The runtime schema was already strict, so none of these ever worked.
- **`coverage` types match the schema.** `coverage.<category>.prefixes` is a non-empty tuple (`readonly [P, ...P[]]`: write `["bg", "text"] as const` or `[first, ...rest]`; an empty list or a computed `RegistryPrefix[]` variable no longer type-checks), and `typography` accepts only `false` or `{ keys: "all" }`, because it has no prefixes and no aliases.
- **Explicit type arguments no longer mistype the options.** `generate()` and `createDesignTokens()` are overloaded: without `options` the tokens carry the library defaults (`readonly ("md" | "lg")[]` breakpoints); with `options`, `const O extends StyleGeneratorOptions = StyleGeneratorOptions` is inferred from the argument. `generate<typeof theme>(theme, { breakpoints: ["xl"] })` (a type argument for the theme only) leaves `O` at its default, so `breakpoints` is `readonly string[]`, never the default literals. Drop the type argument to get the literal `"xl"`.
- **An optional category is `string`, not the defaults.** A theme typed as `ThemeConfig` (a `JSON.parse` result, or an `interface` that `extends ThemeConfig` and does not redeclare `borderRadius` / `borderWidth`) has `borderRadius?` and `borderWidth?`, which may or may not be filled at runtime. `RoundedVariant<ThemeConfig>`, `BorderWidthVariant<ThemeConfig>`, `InferRoundedOptions`, `InferBorderWidthOptions` and `DesignTokens.Web.borderRadius` / `borderWidth` are now `string` / `readonly string[]` for it; 4.x resolved them to the default values (`"none" | "xs" | …`), which was wrong whenever the JSON declared its own keys. A theme whose type declares the category keeps its literal keys; one that omits it (`defineTheme({ colors })`, an `import theme from "./theme.json"` without the field) still gets the defaults. An annotated `ThemeConfig` also makes `colors`, `typography`, `shadows`, … `string` rather than the distinct `Uncapitalize<string>`.
- **`VariantMapperStatesOptions` is removed** (from `.`, `./cva` and `./types`). `createVariantMapper(prefix, tokens, { states })` takes the `{ states }` object inline, so delete the import and pass `{ states: COLOR_STATES }` directly. With a literal tuple (`COLOR_STATES`, `["hover"] as const`) it returns the chained literal (`"bg-primary hover:bg-primary-hover active:bg-primary-active"`, 4.x: `string`); with `readonly string[]` states it still returns `string`. The `{ states }` overloads have three type parameters (`T`, `P`, `S`): an explicit `createVariantMapper<"a" | "b", "bg">(…, { states })` no longer compiles, so drop the type arguments or list all three.
- **`createVariantMapper` prefixes are checked.** `prefix` is `RegistryPrefix | ""` (`bg`, `text`, `border`, `rounded-t`, … the prefixes the registry emits `@source inline` for; `""` is typography). A prefix the registry does not cover (`ring`) is a type error, because it maps to classes no `@source inline` line keeps; so is a prefix held in a `string`-typed variable (`const p: string = "bg"`), which 4.x accepted: type it as `RegistryPrefix` or a literal. Pass `{ allowUnregisteredPrefix: true }` as the third argument to opt out, and add the classes through `extraSources`. That opt-out exists only for a single prefix without `{ states }`; the array-of-prefixes and `{ states }` forms always require registry prefixes.
- **New exports.** `.` (which re-exports everything declared in `src/core`) and `./types` gain `DesignTokensWeb<T, O>`, `ThemeAxisName<T>`, `ThemeAxisVariant<T, A>`, `ThemeAxesState<T>` (every axis optional, each `"base"` or one of its variants; the keys and values are the raw theme keys, while the emitted attribute and selector are kebab-cased: `high-contrast` under `colorMode` is `html[data-color-mode="high-contrast"]`), `BreakpointKeys<O>`, `SpacingKeys<O>`, `ScreenKeys<O>`, `CamelCase` and `KebabCase`. `./types` also gains `SpacingPropertyMap`, `InferRoundedOptions`, `InferBorderWidthOptions`, `InferSpacingKeys`, `DefaultBreakpointKeys`, `DefaultRoundedValue`, `DefaultBorderValue` and `SpacingKey`, which `.` already exported. `GenerateResult<T, O>` is exported from `.`. `Breakpoint` is a value and stays in `.` and `./tokens` only; `./types` ships no runtime code.
- **New token field (runtime).** `DesignTokens.Web.aliasedColors` lists the camelCased color keys whose value is a `$alias` in the base record or in any `themeAxes` override: the holders `coverage.keys: "aliased"` keeps. Its type keeps every key whose value may be an alias: a literal `$…` value counts, a `string`-typed value (JSON import, `ThemeConfig`) counts, any other literal does not; the type only sees the keys that the base record and the overrides declare. Code that builds a `DesignTokensWeb` by hand (a test double) must add the field.
- **`toKebabCase`** is a new runtime export of `.` and `./cva`, the same function the registry and `createVariantMapper` use, so a hand-built class name (`` `bg-${toKebabCase(key)}` ``) matches the emitted one.

## New in 5.0 (additive)

Nothing here changes the output or the types of a 4.x theme; each item is opt-in.

### `axes` option

`options.axes` customises how a `themeAxes` variant is switched on. Defaults reproduce 4.x byte for byte (`html[data-<axis-kebab>="<variant-kebab>"]`).

```ts
generate(theme, {
  axes: {
    attribute: { theme: "data-mode" }, // axis → attribute name; unlisted axes keep data-<axis-kebab>
    scope: "root", // "root" (default): selector pinned to html; "element": no html anchor
  },
});
```

- `attribute` is a plain axis → name map (not a function), so `style-gen.config.json` accepts it too. A name must match `[a-z][a-z0-9-]*` (lowercase like the default `data-<axis-kebab>`), because it is interpolated into the selector. `themeAxisAttributes()` from `./recipes` reads the same map. For every `scope`, an `attribute` key that names no `themeAxes` axis is rejected at `axes.attribute.<axis>`, and so are two axes that resolve to one attribute name (`attribute: { theme: "data-palette" }` next to an axis `palette`). The variant name `base` is reserved (see [Variant named `base`](#variant-named-base)): `"base"` means "no override" and emits no attribute.
- `scope: "element"` emits `[data-mode="dark"] { … }` so the attribute can sit on any element (a scoped theme). A `$`-alias `var()` is still computed where the custom property is declared (`:root`), so `generate()` rejects, as a `ZodError` at `themeAxes.<axis>.<variant>.<category>.<target>`, a variant that overrides a key `target` that another entry aliases (directly or through a chain, in any category) without re-declaring that entry in the same variant. The aliasing entry is looked up in the base theme and in every other variant of every axis. Re-declare the holder (a literal or the same `"$<target>"`) or keep `scope: "root"`.
- `generateThemeCss(theme, options?)` takes the same options as its optional second argument and validates them like `generate()`.
- `generate()` now validates `options` before `theme`; both failures are still a `ZodError`, so only a call with an invalid option _and_ an invalid theme reports a different one first.

### `./recipes` subpath

New subpath `@duydpdev/style-generator/recipes` (browser-safe, not re-exported from `.`): `createTailwindMergeExtension(tokens)` (a `tailwind-merge` 3.x config extension for custom shadows, backdrop-blur, rounded, border-width and typography tokens; `tailwind-merge` stays the app's own dependency), `splitSpacingProps(props, tokens.spacingProperties, unit?)` and `SpacingProps<BKeys, K>` (typed React spacing props → `{ spacing: { className, style }, rest }`), and `themeAxisAttributes(state, { attribute? })` (the DOM attributes of the active axes; `"base"` and `undefined` axes emit nothing; `attribute` is the same map as `options.axes.attribute`).

### `resolveSpacing` first parameter

`resolveSpacing(prop, …)`: the first parameter is widened from `SpacingKey` to `SpacingKey | (string & {})`, so a custom `spacing.properties` key (`resolveSpacing('inset', 4)`) needs no cast. Additive, with one cost: a misspelled prop (`resolveSpacing('pxx', 4)`) is no longer a type error. `resolveSpacingProps` still accepts `SpacingKey` keys only, so it keeps catching typos.

### `style-gen tokens`

`yarn style-gen tokens [--theme <path>] [--out <path>]` writes `theme.tokens.ts` (default: next to the theme) with `export const tokens = {…} as const` and `export type Tokens`: the object `createDesignTokens()` builds at runtime (the keys of `DesignTokens.Web`, no values) serialised as JSON. A client bundle that needs the key lists (a select of color names) imports it instead of the `./tokens` runtime plus the theme JSON (about 2.4 kB gzip versus about 0.6 kB). The theme and options are validated like `generate`; the output must stay inside the project, so a theme outside the root needs an explicit `--out`.

### `style-gen budget`

`yarn style-gen budget <file.css|dir> --max-gzip <bytes>` replaces the `check-css-budget.mjs` script that consumers copied. It sums the gzip size (`node:zlib` defaults) of one CSS file or of every `.css` under a directory (recursive) and prints one summary line, `OK: <n> B gzip across <k> file(s), budget <max> B (<delta>)` or `OVER BUDGET: …`; exit `0` within budget, `1` over, `2` for a usage error, an unreadable target or no CSS. The summary prefixes and the exit codes are the ones the script used, so a CI step that greps them keeps working: replace `node scripts/check-css-budget.mjs <dir> --max-gzip <n>` with `yarn style-gen budget <dir> --max-gzip <n>` and delete the copy. Two differences: an unknown flag now exits `2` (the script ignored it), and error lines (usage, unreadable target, no CSS) carry the CLI logger's `[ERROR]` prefix, so match on the `OK:`/`OVER BUDGET:` summary lines, not on error text.

### `resetTailwindDefaults` option

`options.resetTailwindDefaults: ("colors" | "radius" | "shadow")[]` (also accepted in `style-gen.config.json`) clears Tailwind's built-in namespaces so only your tokens exist. Each name adds `--color-*: initial;`, `--radius-*: initial;` or `--shadow-*: initial;` as the **first** lines of `@theme inline` (the order matters: after the mapping they would wipe the theme's own variables). `"colors"` also removes `--color-white` and `--color-black`; declare them in `colors` if you use `bg-white`. Static utilities (`rounded-full`, `rounded-none`, `shadow-none`) and the `inset-`/`drop-`/`text-shadow` families are untouched. `"colors"` requires a non-empty `colors` record (`colors: {}` is accepted by the schema but would leave `bg-*` with nothing), `"radius"` requires `borderRadius` and `"shadow"` requires `shadows` in the theme: `generate()` throws a `ZodError` at `resetTailwindDefaults.<i>` rather than leave `bg-red-500`/`rounded-md`/`shadow-md` compiling to nothing. The default (`[]`) leaves the CSS byte-identical.

## Generated CSS diff

For a 4.x theme that parses in 5.0, `generate().css` differs from 4.x by exactly these four rules and nothing else:

1. **Color variables.** Every `--sg-<key>` of a `colors` key becomes `--sg-color-<key>`: in `:root`, in every `html[data-<axis>="<variant>"]` block and inside the `@theme inline` mapping (`--color-<key>: var(--sg-color-<key>)`), and in alias values. Variables of the other categories and `--sg-sp-*` are untouched.
2. **Border-width utilities removed.** Every `@utility border-<key>`, `border-x-<key>`, `border-y-<key>`, `border-t-<key>`, `border-r-<key>`, `border-b-<key>` and `border-l-<key>` block is gone.
3. **Border-width theme mapping added.** `--border-width-<key>: var(--sg-border-width-<key>);` is appended, one line per `borderWidth` key, at the end of `@theme inline`. A theme without `borderWidth` (or with `{}`) has no `--sg-border-width-*` variables and gets no mapping, as before: Tailwind's own `border-0/1/2/4` scale applies.
4. **`@source inline` border prefixes.** The border line gains the new prefixes in order:

   ```diff
   -@source inline("{border,border-x,border-y,border-t,border-r,border-b,border-l}-{thin,thick}");
   +@source inline("{border,border-x,border-y,border-t,border-r,border-b,border-l,border-s,border-e,divide-x,divide-y}-{thin,thick}");
   ```

`generate().tokens` has the same values under the renamed keys, plus one new field, `DesignTokens.Web.aliasedColors` (see [Types](#types) above). The exports of `.` and `./types` lose the five `Infer*Keys` helpers and gain the names listed under "New exports" there (`DesignTokensWeb`, `ThemeAxisName`, … on `.` and `./types`; `toKebabCase` on `.` and `./cva`). The byte-for-byte proof of rules 1–4 was run in the renames phase, before those additions: a script applied only rules 1–4 to the 4.2.0 output of 11 cases (the integration fixture with default, no-spacing, all-breakpoints and `extraSources` options; a minimal theme; a theme with every record empty; `examples/theme.json`, `examples/shadcn-theme.json` and `examples/react-v4`; a theme with color `border` next to `borderWidth.thin/thick`; and `typography.cssVarDriven`) and compared it byte for byte with the 5.0 output. The residual CSS diff was empty in every case and the token arrays deep-equal after the rename table above. `aliasedColors` and the new exports do not touch the generated CSS.

Everything else in your build, including the `@theme` breakpoints, the `.sp-*` utilities and typography `@utility` blocks, is unchanged.

## Upgrade checklist

1. Run the grep (or `yarn style-gen doctor` on 5.0) and rename every `--sg-<colorKey>` to `--sg-color-<colorKey>`.
2. Pin the exact version, install, regenerate `theme.css`.
3. Rename `DesignTokens.Web.variant*` / `borderWidthOption` / `roundedOption` and replace the removed `Infer*Keys` helpers.
   The themes in [Stricter theme validation](#stricter-theme-validation) are errors now: rename `fontFamily.weight*`/`size*` keys, typography keys that equal another category's class, and `darkMode`/`dark-mode` variant pairs; break cross-axis alias cycles.
4. Change `spacing.properties` values to arrays if you customised them.
5. Check `typography` keys and `fontWeight` values (`yarn style-gen doctor` reports an invalid theme with its path).
6. Build and look at a page with a border, a swatch and a dark axis: transparent swatches mean a missed variable.
7. Rename any `themeAxes.<axis>.base` variant, drop a leading `/` from `--theme`/`themePath` values that meant a project-relative path, and remove unknown flags from `style-gen` calls (they are errors now).
8. If you create a Vite dev server programmatically, `await server.listen()` before reading `theme.css`; replace a copied `check-css-budget.mjs` with `style-gen budget`.
9. Look for `style-gen schema --theme …`, `style-gen doctor --theme …`, a flag placed before the command (`style-gen -w generate`) and positional arguments on `doctor`, `schema` or `init` in `package.json` scripts, CI files and docs: they exit `1` now (see [CLI](#cli)).
10. If you call `styleGenVite()` / `styleGenNext()` with no arguments, restart the dev server after editing `style-gen.config.json` (the plugins read it once); pass an options object, or run `style-gen generate --watch`, if you need live config edits.
